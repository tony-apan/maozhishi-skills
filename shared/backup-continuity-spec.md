# 备份与换账号接续规格（整仓共用）

本规格是贸知事技能仓全仓共用的一份：建站、来发信及以后接入的模块都按本规格执行备份与换账号接续，不许各模块各写一套。依据：《数据不丢与换账号继续》定稿方案（2026-11-19 定稿，历经多轮异厂对抗审查）。建站 SKILL 第十节的同步与迁移五步是本规格的前身口径，互斥证据与独占执行机制仍以第十节现行清单为准，本规格引用、不另设一套。

## 一、总则

1. **保哪一层，先说清**：用户数据分三层——平台层（来发信平台、LaiCMS 后台里的数据，换 Muse 账号重新登录/授权即可，不归备份管）、台账层（Google 表格或本地 xlsx 台账，见第三节同步清单的补强）、工作区层（只存在于当前 Muse 账号工作区里的档案、记录、口径与交接，是唯一真风险）。**备份地保的就是工作区层**，不承诺「所有数据一键全回来」。
2. **本地主本**：用户本地工作区永远是主本，备份地是副本。同步失败不许拖住每日业务，本地照常跑，失败只报不堵。
3. **能力降级总则（硬规矩）**：本规格里一切自动化能力以实测结论为生效条件。当前证据状态：GitHub 连接器代建仓**未验证**——落版默认口径是「用户点预填链接自建仓、AI 随后接手校验与同步」，任何文件、话术都不许把「AI 自动建仓」写成默认能力；代建仓实测通过后，再按实测改写本条。云盘建文件夹、可见性读回等能力同样逐项标证据等级（已实测／仅文档／未验证），未验证的按半自动说法写。
4. **凭据红线**：任何密码、令牌、授权文件永不进备份地、永不进索引与登记——索引里只记账号标识与路径（见第五节）。
5. **命名硬规矩**：备份仓名、云盘文件夹名、工作区分区名，以及备份地与工作区内的文件夹名、文件名，一律英文、禁止中文命名（分区名用英文小写短横线式，见第七节）。

## 二、备份地与一账号一仓

1. **默认一处**：每位用户定一个备份地。默认推荐 GitHub 专属私有仓；Google 云盘文件夹是平权备选，按用户习惯选。技能在 Muse 上运行，连接与同步走 Muse 云端，不存在用户本地网络连不上 GitHub 的问题，取舍只看习惯。
2. **一账号一仓**：普通用户只引导建一个 GitHub 账号、一个仓，装下全部内容——不按技能拆仓、不让用户管多个仓。
3. **可选双备份（主备制）**：用户想要更稳妥，可以 GitHub 与云盘两个一起开：一个为主、一个为备（默认 GitHub 为主、云盘为备，可按习惯反过来）。每日收尾先同步主、再同步备，日报里两处状态分别报。双备份是可选项，引导时当场问一句即可，默认不开。
4. **可以先不设**：用户暂时不设的，不硬卡开工，但必须把「不备份＝Muse 账号丢失时工作区数据接不回来」讲清，并把未设状态记进工作区根索引与 90 交接层（见第四节记录点）。未设期间按第十二节的提醒节奏温和提醒。
5. **整仓统一记录点**：备份地的选定结果（选了哪处、主备角色、地址/路径、账号标识、何时定的）只记一处真源——工作区根索引的「备份地记录」段，90 交接层放一份镜像。两个技能开工都先读它：已定就沿用、不重复问、不重复建；未定才由当前开工的技能按第十二节引导。
6. **与建站「文章存档地」的关系**：建站开工第五步原有两个「地」——文章存档地（只存文章 Markdown 原稿，云盘与 GitHub 二选一）与全量工作备份地。本规格管的是全量工作备份地，并把它升为整仓统一；文章存档地口径不变，仍按建站 SKILL 现行条文执行，两者不要混（定版：文章存档地不并入 `allincms/` 分区，两套东西分开管）。

## 三、固定命名与备份地布局

1. **固定名全线统一**：备份地（GitHub 仓与云盘文件夹同名）＝ `maozhishi-backup`；标记/索引文件 ＝ `maozhishi-backup.json`（放备份地根目录）；状态日志文件 ＝ `maozhishi-backup-log.md`（放备份地根目录，见第九节）。固定坐标是换账号自动发现的地基，不让用户自己起名。
2. **GitHub 侧布局**：根目录放索引 `maozhishi-backup.json`、状态日志、说明书 `README.md`（见第六节）；数据按分区目录存放（`memory/`、`laifaxin/`、`allincms/`、其余注册分区、`misc/` 垫底）；快照以散文件提交＋标签承载（见第八节），不另设快照目录。
3. **云盘侧布局**：根目录放索引、状态日志、说明书，与 `snapshots/` 文件夹（zip 快照存放处）；zip 内的目录结构与 GitHub 仓内一致。
4. **分区列序定版**：第一 `memory/`（记忆）、第二 `laifaxin/`（来发信）、第三 `allincms/`（独立站），其余模块分区按登记先后排在后面，`misc/` 垫底。此顺序同时是索引里的分区列序、日报里备份状态的报序、换账号接续时的拉回顺序。
5. **建侧撞名处置**：建仓/建文件夹时固定名已被占用，先读对方有没有标记文件——有且验得过，是用户自己的旧备份，直接沿用；没有或验不过，停下问用户（可能是他的无关同名仓），不许往里写、不许擅自改名另建。

## 四、备份地记录点与优先序

记录点口径在第二节第 5 条（整仓唯一真源＝工作区根索引的「备份地记录」段，90 交接层放镜像）。读取顺序定死：两个技能开工先读根索引记录段、再读 90 交接镜像。本地记录与备份地索引对不上时，先对账（第十节），**以备份地索引为准重建本地记录**——备份地索引是恢复真源，本地记录是缓存；接续场景同理。

## 五、索引文件 `maozhishi-backup.json` 全字段

索引不只是标记文件，它是备份索引；但它不是唯一真源——每份快照的 manifest 自带全套身份信息，索引损坏或丢失时可由 manifest 汇总重建（见第八节第 6 条）。

| 字段 | 内容与口径 |
| --- | --- |
| `formatVersion` | 备份格式版本（整数）。只增不改旧义；每版字段结构随技能仓保存一份格式规格；缺字段按规格默认值处理；遇到比自己认识的还新的版本，停机报错、不猜不读（见第七节第 4 条） |
| `backupId` | 备份唯一标识：首次创建时生成的随机串，终身不变，是验身与防误认的根 |
| `createdBy` | 创建账号标识：`type`（github／google-drive）＋账号标识（GitHub 登录名／Google 邮箱）。只记标识，不是凭据 |
| `createdAt` | 首次创建时间 |
| `skill` | 技能登记段：技能仓名、整仓版本、各模块及版本、官方安装地址、公开仓地址。建仓时写入、每次快照时更新（全字段见下） |
| `partitions` | 分区注册表：每项含分区英文名、所属模块、创建时间，按第三节第 4 条列序（见第七节） |
| `locations` | 备份地登记表：每处一份登记（全字段见下），双备份时两处互相记着对方 |
| `snapshots` | 快照列表：每份含序号、生成时间、形态与位置、校验摘要、文件数（停用状态不写在这里，见第九节） |
| `snapshotCounter` | 快照计数器当前值：已发放的最大序号（含已停用号），续号规则见第八节第 4 条 |
| `exclusions` | 备份排除清单：用户明确说不要备份的东西，只留名，以后不再反复问、也不进快照（见第七节第 5 条） |
| `retention` | 保留策略状态：云盘现存份数与总量、GitHub 仓体积、单文件预警状态，最近一次清理时间 |

`skill` 段全字段：

```json
"skill": {
  "packName": "贸知事技能仓",
  "packVersion": "<整仓版本>",
  "installUrl": "https://skill.maozhishi.com",
  "publicRepo": "https://github.com/tony-apan/maozhishi-skills",
  "modules": [
    { "id": "laifaxin-leadgen", "name": "来发信", "version": "<当前版本>" },
    { "id": "laicms-site-builder", "name": "建站", "version": "<当前版本>" }
  ]
}
```

`locations` 每处登记全字段：

```json
{
  "type": "github",
  "role": "primary",
  "account": "<GitHub 登录名或 Google 邮箱>",
  "name": "maozhishi-backup",
  "folderId": "<云盘文件夹 ID，GitHub 处为空>",
  "path": "<云盘路径，人读参考；GitHub 处为仓地址>",
  "lastSnapshotSeq": 12,
  "lastSyncAt": "<ISO 时间>"
}
```

云盘文件夹 ID 不随改名与移动变化，比路径可靠，必须记；路径同时记作人读参考。本地工作区交接里再记一份同样的登记（三处互备）。

## 七、分区注册制

1. **分区不是写死的**：索引里维护分区注册表。现行三席：`memory/`（整仓共用，记忆）、`laifaxin/`（来发信）、`allincms/`（建站）；常设 `misc/`（杂项）。
2. **新模块自动登记**：以后新模块（社媒运营、广告投放、B2B 运营等）开工时，自动登记一个自己的分区（如 `social/`、`ads/`）就并入同一套备份，不用改备份格式、不用问用户。登记校验：名字必须是英文小写短横线式、与已有分区不重名，写进注册表之后才许往里放文件。
3. **分区内分层**：各模块分区内沿用现行 30/40/50/90 的分层习惯（任务、产出、数据、交接）；根目录只留真正共用的东西（公司事实档案、品牌口径等，即现行 20-knowledge 的共用部分）与整仓级文件（根索引、90 交接层）。
4. **格式演进**：`formatVersion` 只增不改旧义；新版技能必须能读所有旧格式快照；格式升级时旧快照原样不动、恢复时按各自的格式读；遇到更高 `formatVersion` 停机不读（见第五节）。
5. **待问区与排除清单**：日常工作中冒出来的、归不进已知分区的新东西，先放 `misc/` 的待问区——**只存本地、不进任何外部备份**，并在当日日报里问一句「这份 XX 要不要长期备份」：用户说要，才归位到对应分区（没有就新建并登记）并从此进快照；说不要，记进备份排除清单（索引 `exclusions` 留名），以后不再问、也不进快照；一直没答复的，一直只留本地，每周在日报里至多再提一次。

## 八、同步清单、快照与编号规则

### 8.1 同步清单（两技能同一张，按分区逐段）

- `memory/` 分区：用户档案、已定口径与重要决定、分主题业务记忆、未完成事项清单。（记忆是第一分区，快照与校验清单必须含它，漏了它「先拉记忆回血」就落空。）
- 根共用区：业务/产品事实档案（公司档案、产品事实、卖点与已定口径）。
- `laifaxin/` 分区：计划与排期、日报、开发信稿、搜索日志、公司去重总账、公司级开发状态（公司名、域名、开发阶段、发到第几封、回没回、下一步日期）、**本地台账 xlsx 本体**、交接文件。
- `allincms/` 分区：计划与排期、文章原稿与发布记录、站点设置记录、交接文件。
- 其余注册分区：按该模块在注册时登记的清单执行；`misc/` 分区只含已归位的东西，待问区永不进快照。

### 8.2 永不进备份地（红线）

任何密码、令牌与授权文件；聊天与邮件原文；一切联系人明细——**唯一例外是台账本体**（含联系人明细，按 8.3 的披露与同意口径、经用户明确同意后才进；台账之外的任何联系人明细摘录仍一律不进）。

### 8.3 台账进备份的如实披露（启用前必办）

台账本体含联系人姓名/邮箱/电话。它进备份，等于这些明细会上传到 GitHub／Google 这类第三方云服务商的服务器、存进用户本人名下的私有备份地。口径写死：**不许说「不是传给第三方」**——平台就是第三方；能打开的范围由用户账号的权限设置决定（私有仓默认只有本人、云盘默认未共享），但数据托管在服务商服务器上，**不许承诺「只有本人能看」**。启用含联系人明细的备份前，必须把这一点讲清并取得用户明确同意；不同意的，台账本体不进备份，只备公司级状态，并显名告知代价（换账号后客户明细接不回来、只剩公司级状态）。理由也讲清：台账是获客的命根子，不备它，换账号后日常开发接不回来。此条修订建站现行「联系人明细不进仓」口径，修订范围仅限台账本体。

### 8.4 快照形态：逻辑统一、物理分平台

一份快照＝一个全局递增序号＋一份清单（manifest），两处共用此逻辑模型；物理存法按平台分开：

- **GitHub 侧用散文件**：每次同步把工作区文件直接提交一次（commit），给该提交打标签 `snap-<序号>`（如 `snap-003`），git 历史本身就是快照序列，manifest 随提交进仓。不许把 zip 塞进 GitHub（删 zip 不释放 git 历史空间、单 zip 超 100MB 会被拒收）。
- **云盘侧用 zip 包**：放 `snapshots/`，命名 `maozhishi-backup-<日期>-<序号>.zip`（如 `maozhishi-backup-2026-11-19-003.zip`），zip 内带同一份 manifest，zip 内目录结构与仓内一致。

### 8.5 快照编号规则（生成事件发号）

1. 编号是「内容版本」号，在**生成**一份全量快照的那一刻由本地工作区发放：本地索引计数器每生成一份 +1。
2. 号跟着「生成事件」走，不跟存放地走：云盘每 3 小时生成一份、领一个号，只存云盘；GitHub 每日生成一份、领新号，只存 GitHub；**只有同一份快照被分发到两处存放时，两处才同号——同号同内容天然成立，因为是同一批文件、同一份清单**。不存在「把一份内容沿用另一个号」的操作。
3. 恢复取舍：不无条件以主为准——在两处全部已登记快照里取**号最大且校验通过**的一份（主同步失败、备更新时用备；同号两处都有时先逐文件对哈希，一致取主、异容按第九节停用该号取次新）。用了备要显名告知用户；用备恢复后，等主恢复可用时，把这份最新内容在主处生成一份新快照对齐，再继续日常同步。
4. **续号**：计数器丢失或索引重建后，先完成对账认领（第十节），计数器取「全部已登记快照的最大号」（含已停用号，号只增不减、永不重用），下一号＝最大号+1。**先对账、后发号**，对账完成前不许生成新快照。
5. GitHub 上的记忆实时提交是普通提交、不占快照号（见第十一节）。

### 8.6 同步顺序（定死）

生成快照 → 远端落盘 → 读回校验（按 manifest 逐文件对哈希）→ **校验过了才在索引里登记这份快照**。中断的快照不登记，靠对账环节处理（第十节）。同步以整仓为单位、由统一收尾动作执行，同一时间只许一个同步在跑（锁，见第十一节）。每次往备份地推之前，先过公开仓检查（第十三节）。

### 8.7 manifest 必含

`formatVersion`、备份唯一标识、快照序号、生成时间、分区注册表与 locations 的当时副本、逐文件清单与 sha256、明确列出的排除项。manifest 随快照定格、**不含事后状态**——停用等状态变化记在索引与状态日志里（第九节）。文件清单只列数据文件、明确排除索引/标记文件自身，免自引用；清单按分区列序分段列。

## 九、同号异容与状态日志

1. **同号异容处置（定死）**：同一号在两处逐文件哈希对不上 → 该号两份都**停用**、不作恢复源；恢复自动跳过它、取次新的校验通过份；同时标报警进日报显名（见第十四节）。多为一处同步中断或内容被改动所致，先查清原因；查清后是否恢复该号，由用户裁决，其余步骤不等人裁。不自动覆盖、不自动合并。
2. **停用状态怎么存**：不写回 manifest（写回会改快照内容、坏掉校验）。停用记两处：索引的停用列表（由快照列表派生维护）、备份地根目录的**状态日志**文件 `maozhishi-backup-log.md`（独立于任何快照内容的常驻文件，只追加、不改旧行；每行记时间、快照号、动作、原因）。
3. **双写取并集**：双备份时状态日志两处都写，随每次同步对齐；索引重建时从任一幸存处回放。两处日志内容不一致时，停用记录取**并集**——被任一处停用过的都算停用，宁严勿松。
4. **兜底**：重建对账时同号异容会被重新检出并重新停用，状态日志丢了也漏不过去。单处备份、索引与状态日志又同丢的极端情况，显名告知用户「停用记录已失、按现存内容重建」，请其确认，不许默默当无事发生。

## 十、对账认领

每次同步开始前、每次接续发现时，先做一次对账扫描（远端实际内容 vs 索引登记）：

1. 未登记的快照：先读它自带的 manifest 与身份信息，验 manifest 与哈希——验得过就补登记（认领）；验不过（无清单／身份不符／哈希对不上）就隔离并显名报用户裁决，不许当不存在悄悄跳过、也不许自动删。
2. 两处索引不一致时：以「快照实际存在且校验通过」为准重建索引再继续；重建时先汇总各份 manifest，再回放状态日志恢复停用状态（第九节），已停用的号重建后仍是停用、不许复活；重建完让用户确认。
3. 与 8.6「校验过才登记」不矛盾：那条管生成当场不当场标有效；对账是事后补救——内容完整、只是登记中断的，验过补登；内容不全的，隔离。

## 十一、分层频率、写入串行与记忆实时同步

### 11.1 分层频率

- **GitHub**：记忆与关键状态变更即推（实时层）＋每日收尾一次全量快照提交（日层）。
- **云盘**：每 3 小时一份全量 zip 快照，不做增量链。
- **记忆同步随备份地走**：实时层只在用户选了 GitHub 时成立；只选云盘的，记忆随云盘 3 小时快照走，代价显名（记忆最多差 3 小时）；未设备份地的，记忆只存本地工作区，按提醒节奏提醒，不许出现「要求实时推、却没有可推的地方」的悬空规则。

### 11.2 写入串行（整仓锁）

1. GitHub 侧所有写入（实时记忆提交与每日快照提交）走同一把整仓锁、按时间排队，一次只跑一个。
2. **锁的优先级定死**：记忆实时提交优先放行（小而快）；每日全量快照生成前，先等在途的实时提交完成再冻结（冻结的对象是本地工作区的文件集）；**等待上限 15 分钟**，超时不等了，快照按本地当前状态冻结生成，在途的实时提交随后照常补推、互不影响。
3. 实时提交排队期间不阻塞本地落盘：记忆先写进本地工作区，提交在 5 分钟合并窗口内异步补推（连续变更设 5 分钟合并窗口防碎提交）。
4. 每次提交前先拉最新状态再写，防覆盖；提交失败自动重试一次，再失败把变更留在本地待同步队列、次日日报显名报——本地主本一直在，变更不丢、只是晚到。
5. **跨环境独占**：整仓锁只管单个环境内。用户在两个 Muse 环境/设备上同时用时，靠独占口径兜底——同一时间只许一个环境写备份地（沿用建站第十节的独占执行机制），另一环境只读；两端同时收尾同步禁止，冲突变更一律进待同步队列、不许强推覆盖。

### 11.3 记忆分区

1. `memory/` 是一等分区：用户档案（称呼、时区、业务与偏好）、已定口径与重要决定、分主题业务记忆、未完成事项清单。
2. **写入纪律**：只存淬炼精华（结论与要点，不存流水账）；确认即回落（用户确认了新事实/新口径/新决定，当轮就写进记忆文件，不攒）。
3. **记忆治理**：写入前过敏感筛——联系人联系方式明细、凭据、聊天与邮件原文永不进记忆，记忆只存事实、口径与决定本身；用户随时可查可删（他问「你记住了我什么」就如实列出，他说删哪条就删哪条；删除同步处理当前文件，历史版本里的旧副本按第十五节删除实话口径处置，不承诺无痕）；停用或换号时，旧备份里的记忆副本处置在接续/停用话术里显名交代，不默默留着。
4. **记忆清单与恢复校验**：每次记忆实时提交随附一份 memory 清单（文件＋sha256）。恢复时按最近一份清单逐文件验哈希；验不过就沿提交历史回退到上一个记忆提交再验，直到验过为止——只有验过的版本才用来「回血」，不许拿没验过的记忆直接恢复。
5. **记忆恢复的特例**：GitHub 侧恢复 `memory/` 时，取备份仓当前最新提交里的 `memory/` 目录状态（实时提交都在里面，比最近一份全量快照更新），其余分区才按快照取。快照停用的粒度只针对该快照的非记忆分区，`memory/` 的恢复独立于快照停用——哪怕最新提交正是一份被停用快照的提交，它的 `memory/` 部分仍可取用（仍须过本条第 4 款的清单验哈希）。云盘侧记忆随其最新快照。

## 十二、引导三段与一次办完（口径摘要，话术正文在各 SKILL）

1. **第一段·安装/首次检查**：当场引导关联 GitHub 并建仓（一个账号、一个 `maozhishi-backup` 私有仓，当场校验私有、写好索引），当场讲清好处与风险：备份还存在用户自己的 GitHub/云盘账号里，Muse 账号被封了，换个账号装上技能、连上备份就能接回来；备份范围当场说清（台账、进度、文章与记忆；邮件和聊天原文不进备份）。暂不关联的，不硬卡开工，记下意向按第三段节奏提醒。
2. **一次办完清单**（安装向导合并成一个流程，一次点完）：① 发确认句；② 关联 GitHub → 建 `maozhishi-backup` 私有仓 → 当场校验私有、写好索引；③ 顺手关联 Google → 建云盘备份文件夹 → 双向登记一次写好（双备份，不想开的跳过此项）；④ 给技能仓点 Star＋Watch（用户本人点，或他点头后 AI 代办，不搞没经同意的自动星标）；⑤ 备份参数全默认，用户零配置；⑥ 设好每日定时任务与巡检；⑦ 如安装时已有工作数据，当场跑首次全量同步并读回核验。首次全量同步的触发规则只有一条：**数据第一次出现时做**（装机时已有就装机时做，没有就等第二段触发点）。办不了「一次」的显名：平台授权到期要续（届时提醒）、记忆长期积累、恢复演练在接续时做——不硬塞进安装流程。
3. **建仓的默认动作（降级口径，硬规矩）**：GitHub 代建仓未实测验证前，默认是**用户点预填链接自建仓**：给用户 https://github.com/new?name=maozhishi-backup （仓库名已写进链接、打开即预填），话术逐项讲清——可见性选 Private、其余不动、点 Create repository；建好后 AI 接手：读回校验私有、写索引与说明书、跑首次同步。代建仓能力实测通过后，再把默认动作改回 AI 代办，并同步修订本条。
4. **第二段·首次产生真实数据后**：触发点任选其一先到为准——台账建好、第一批客户入池、第一篇文章定稿。第一段已建仓的，本段只做首次全量同步与补云盘（双备份）；第一段跳过了的，本段才走完整设置（连接授权 → 建仓/建文件夹 → 读回校验私有与共享范围 → 首次全量同步 → 读回核验 → 备份状态写进日报模板，以后每天一行，双备份两处分开报）。
5. **第三段·没设的温和提醒**：未设备份地的，日报里每周至多带一行提醒，不天天催；工作区里有了成规模的客户数据（如候选池过百家）再正式提一次。设了的，同步失败当天日报显名报。
6. **用户侧动作清单要短**：核心动作只有两件——在连接授权页点允许、（没账号时）先注册一个；Star/Watch 是顺手项，他愿意才点。建仓按第 3 条默认动作走时，用户多一件「点预填链接建仓」。其余校验、同步、核验全由 AI 办。话术里不许把用户动作说得比实际少。

## 十三、公开仓专项检查（fail-closed）

1. **查什么**：备份仓是不是公开仓、云盘文件夹是不是被共享/开了公开链接。
2. **三处落点**：建仓后当场查、每次同步前顺带查（推前校验）、每日收尾再巡检一次。写进开工三件事与每日巡检，漏查视为备份流程未完成。
3. **查到公开的处置**：立即停推新数据，高优先级提醒用户务必改私有，附手把手改法（GitHub 仓库 Settings → General → Danger Zone → Change visibility → Private；云盘关共享与链接）。提醒必须带一句实话：公开期间的数据可能已经被别人看到或抓走，改私有只是止血、不等于撤回泄露；公开期间推过台账等敏感内容的，按已泄露处置并显名报用户。用户改完，AI 读回确认已私有才恢复同步。
4. **fail-closed（定死）**：可见性读不到、连接器报错、结果不确定时，一律按「不安全」处理——停推并提醒用户，绝不默认放行。此项能力列入前置实测，实测不过，GitHub 通道不启用。

## 十五、风险与边界（显名）

1. **不加密（显名决策）**：快照不加密。备份地已是用户本人私有空间，防线是账号本身；加密密钥对非技术用户是更大的丢数据风险（密钥一丢，备份全废）。代价是平台方理论上能接触内容，与私有仓/云盘的一般信任模型一致。
2. **校验的边界**：校验和防的是损坏与误认，防不了备份地账号被攻陷后的连同哈希一起篡改；标记文件验身只能防「误撞同名仓」，防不了投毒。安全边界就是账号本身，话术与文档不许把验身说成防攻击机制。
3. **解压安全（硬规则）**：恢复解压时拒绝带 `../`、绝对路径与符号链接的条目，只许写进隔离区内。
4. **删除说实话**：用户要求删某客户数据时，台账与备份地的当前文件当场删并记删除记录；但 Git 历史提交与云盘版本记录里可能仍有旧副本，不许承诺「删了就全网无痕」。需要彻底清除时，由 AI 代办历史清理（重写仓历史/清空云盘版本）并显名告知做了什么、做到什么程度。
5. **备份不是授权**：新账号恢复数据后，仍须重新亲口确认、重新绑平台，任何文件都不许自带授权效力。
6. **备份地账号本身的风险**：GitHub 或 Google 账号被封/遗失时单备份就断了，这正是双备份的意义；处置见第十六节第 8 步。

## 十六、换账号接续八步

新账号装好技能仓（还没装的，备份仓根目录的 README 说明书会指路先装），开工检查发现是新环境，先别走新用户全套向导，先问一句：「你以前用过贸知事技能吗？」答没用过的，按新用户走；答用过的，走下面八步。**用户什么都不用记、不用报路径。**

1. **自动发现与初筛**：请用户连接备份地账号（设了双备份的 GitHub 与 Google 都连，只设一处的只连那一处），AI 按固定坐标自动去找——GitHub 名下有没有 `maozhishi-backup` 仓、云盘根目录有没有 `maozhishi-backup` 文件夹。找到后读索引初筛：格式版本对得上（更高版本停机不读，见第五节）、备份唯一标识在、创建账号与刚连接的账号一致（对不上就停自动恢复、转人工确认，可能是他换了备份地账号，要他亲口认，走第 8 步）；把「最后同步时间」报给用户看，他点头才拉。双备份两处都找到的，先互读对方索引里的 locations 登记核对。**「读不到」与「对不上」分开处置**：一处暂时读不到（连不上、索引缺失）→ 不停，按第 7 步从读到的那处继续、后补登记；两处都读到了但内容对不上（唯一标识、账号标识、快照号矛盾）→ 停下走人工确认，不许猜着认。取数按 8.5 的恢复取舍：在两处全部已登记快照里取号最大且校验通过的一份，同号先对哈希、异容停用取次新。自动发现找不到的才走兜底：列出他名下其他仓库/文件夹让他认领（改过名的情况），再查旧日报发到通知邮箱的记录等线索；实在找不到，才按新用户走，并当场显名告知「旧数据这次接不回来」的原因，不许含糊带过。
2. **隔离区关卡链（顺序钉死）**：拉回先进**隔离区**（新工作区旁的待验目录，不直接进正式工作区）。在隔离区内依次做：**第一关验全量**——按这份快照的 manifest 对全部文件逐个验哈希（根索引、交接文件也在内，一个不漏），对不上的文件标出、整份按验不过处理；**第二关验记忆**——`memory/` 另按 11.3 第 4 款的记忆清单再验一遍（记忆有独立的实时提交清单与回退机制，与第一关的全量验是两重校验、不算重复），验不过沿提交历史回退再验，**回退到头仍验不过的文件不恢复、显名列进缺失清单请用户确认**——用户确认后二选一：接受缺失继续走后续关卡（缺失项记进交接、启用后靠日常使用逐步补回），或放弃本次回退、整份隔离内容作废重拉一份；此处置是隔离校验关内的分支，不适用第 6 步演练关的人工替代（替代仅限演练关本身）。其余验过的文件才用来复述关键事实让用户确认。两关都过，才把内容并入正式工作区 → 再读根索引与交接文件接业务状态（只读接状态，先不启用任何每日任务）。记忆复述发生在并入之前，不许先并入再补验。失败处置分两种、不许混用：**第一关全量验不过**（任一文件哈希不符即算）→ 整份隔离内容删掉、走认领兜底，正式工作区不受污染；**第二关只有个别 memory 文件验不过** → 走上面缺失清单的用户确认分支（接受缺失继续或放弃重拉），不整份作废。
3. **重新确认**：备份恢复的是数据、不是授权——确认句必须由用户在新账号里重新亲口发一遍，记入新账号记忆后再继续。
4. **重新绑平台**：来发信重新走官方授权（设备码）、LaiCMS 密码在新账号保险库重新存一次、Google 重新授权——凭据一律不从备份地迁移（备份里本来也没有）。
5. **互斥与对账后才启用**：沿用建站第十节迁移五步的门槛——先拿到旧账号每日任务已停用的可验证证据（或独占执行机制），再逐项对账（台账、发布记录、开发进度），最后才逐项启用新账号的每日任务。旧账号登不上、停没停确认不了的，新任务保持暂停并显名报，不许假定已停。证据的取得办法以第十节现行清单为准。
6. **真恢复演练**：只读回核对证明不了能恢复——首次同步完成后，AI 自动把备份地拉到隔离区（与第 2 步同一套规矩：只在区内解压校验、不过整份删），按同步清单逐项核对关键文件齐不齐，再只凭这份拉回的文件复述当前业务状态（在开发谁、发到哪一步、下一步干什么），两样都对上才算备份有效。演练不过：当场标「备份未验证通过」、回补一次同步并重演；仍不过写进日报显名报用户，接续/迁移场景下演练不过不许启用新任务。**人工替代出口**：AI 把对不上的项逐条列清给用户，用户逐项认或改，认完按「人工逐项确认接续」继续，并在交接文件里记明「本次接续未过自动演练、系人工逐项确认」；缺失项补齐后可随时重演、不限次数。接续全程的关卡是串行的一条链：隔离校验 → 记忆确认 → 互斥证据（第 5 步）→ 备份对账 → **重新确认（第 3 步）→ 重新绑平台（第 4 步）** → 恢复演练（本步）→ 启用——第 3、4 步是启用的前置关：确认句没重新发、平台凭据没重绑完，不许进演练、更不许启用（没绑好就启用，任务一跑必失败）。任一关不过都保持暂停并分别显名卡在哪一关，不许跳关；**「演练不过不许启用」的唯一例外是本步的人工替代出口**（用户逐项确认后视为演练关已过、可以继续启用，交接与日报统一标「人工逐项确认接续」）；**替代仅限演练这一关，前序各关（隔离校验、记忆确认、互斥证据、备份对账、重新确认、重新绑平台）不得用人工确认替代**（第 2 步 memory 缺失的用户确认分支是隔离校验关内的既定处置、不是替代，不在此禁列）；替代后下一次成功同步自动补演一次。顺序说明：互斥证据与备份对账排在重新确认/重新绑平台之前，是先确认旧侧已停、本地与备份地的文件与索引对齐——**此处的对账只对本地与备份地，不读平台数据、不需要平台凭据**；需要平台实时数据的业务对账（如平台侧联系人状态）排在重新绑平台之后、恢复演练之前做。确认与绑平台是新侧启用前的最后两关——确认句记入新工作区 `memory/` 的决定记录、不依赖平台绑定，新工作区（位置与空壳）在隔离校验开始前已由用户就位——隔离内容整份删除走认领兜底时，工作区壳仍在、重拉后从隔离校验关重走，不影响就位前提。之后每季度由每日任务顺手自动再演一次（AI 发起、用户零负担，只在不过时才报；此条以实测结论为生效条件，未实测通过前降级为日报提醒、不作自动承诺）。另注意单备份地的固有风险：同步会把本地的误删/误改也传上去，GitHub 侧靠完整提交历史可回退；云盘侧的回退窗口有限（30 天内逐日份、更早只有月末份，口径见第十七节），演练时顺手确认回退路径在窗口内存在，并把窗口限制按第十七节口径记进交接（记明可退到哪一天、哪一份）（此确认随演练发生、不单独承诺频率）。
7. **单备份与一处失联的接续**：只设了一处备份地的，接续只连登记的那一处，不要求两处齐全。双备份一处暂时失联（平台故障/账号一时登不上）时，允许从另一处恢复，恢复时显名告知这次用的是哪一处、数据新到什么时间；等失联处恢复后再对账补齐，并把这次接续记进交接。一处索引读不到/两处对不上的区分处置，按第 1 步的规则办，不在此重复立规。
8. **备份地账号也换了/丢了**：第 1 步初筛「创建账号对不上转人工」的处置就是本步。旧备份地账号还能登录的：把仓/文件夹转移到新账号（GitHub 仓转移、云盘移交所有权），或把新账号加为协作者，再更新索引里的账号标识与 locations 重新登记。旧账号彻底登不上的：该处备份视为丢失，只能靠另一处备份地接续（这正是双备份的价值），并显名告知用户丢了哪一处、数据新到何时；单备份且那一处账号丢失的，旧数据接不回来，按新用户走并当场重建备份——结论显名，不许含糊。

## 十七、保留策略

1. **GitHub 侧不删**：不做删除清理——git 历史删文件不释放空间，清理无意义，全部提交历史天然保留，仓体积靠「不变文件共享存储」自然收敛。万一仓体积异常膨胀，处置是迁移：以最新快照为起点新建仓、旧仓归档只读（罕见情形，显名报用户后办）。
2. **云盘侧分层保留**：48 小时内逐份留（约 16 份）、此后 30 天内每天留 1 份（取当日最后一份成功快照）、更早每月留 1 份（月末最后一份）、**月度份只保留最近 12 个月、到期清理**；常态约 58 份（16＋30＋12），总量≈单份大小×58。索引持续监控，总量超阈值先提醒用户再清理；清理（含月度份到期清理）前必须先完成双边对账、索引不一致时一律禁止清理——到期遇对账未过，清理顺延到对账通过后的下一个清理窗口（清理检查随每日全量快照后执行，窗口即每日一检），先在日报预告一行、清理当日再记账一行，两行不许省。**回退窗口如实口径**：云盘侧误删/误改的回退只在保留期内成立——30 天内可退到逐日份、更早只能退到对应月末份（月末份本身已含误改的，回退不到干净版），不许宣称云盘侧可任意回退；GitHub 侧靠完整提交历史回退、无此窗口问题。
3. **容量预警**：单文件超 25MB 预警（多半是视频等大文件混进了工作区，那类东西不该进这套备份；GitHub 单文件 100MB 是硬拒收线，必须远离）；云盘总量与 GitHub 仓体积分别记入索引 `retention`。
