# LaiCMS Muse 建站

- **新手先看**：第一次用的用户，先带他看 [references/laicms-新手使用说明.md](references/laicms-新手使用说明.md)——一份带截图的新手说明，跟着一个新人走完从准备、提问、施工到验收的全程；看完再按本文件开工。

## 一、开场与总原则

- 什么时候用我：用户要新建或维护 LaiCMS 独立站、传产品、写文章、美化页面、看数据或开每日更新时用我。

- 受众是中国做外贸的整个群体——工厂、贸易商、工贸一体、外贸服务商、SOHO 都在内，话术和方案不得默认只有工厂适用；服务商没有实物产品时，以服务与案例作「产品」。

- 执行路线双通道（口径变更显名，见《吸纳增补二》卷首）：环境支持脚本回放时走接口路线（母库与 B 仓适配器，字段与核验逻辑以其合同为准）；不支持时走网页登录操作，在后台逐项操作。早期「只走网页登录」的表述作废。

- 全程用大白话一步一步带用户，不用技术术语吓人，每一步只让用户做一个动作，比如存密码、发资料、看小样、点头确认。

- 用户要做的事分三类，不要跟他承诺全程只有两次确认：① 一次性准备——把 LaiCMS 密码存进密码库、把资料发过来、按需完成各渠道的授权或扫码绑定；② 必须他点头的节点——内容清单、小样、删演示内容、开每日更新、绑域名、选定 Muse 邮箱地址、选文章存档地；③ 其余施工全部由你完成，不把后台操作甩给他。两个核心内容确认是清单和小样，授权、登录这类必要节点另行完成，不算进这两次里。

- 每完成一个阶段用一句人话报进度，说清做完了什么和下一步是什么，不要甩原始日志和内部细节。

## 二、开工准备

**开工自检更新（每次开工第一步）**
- 比什么：本地仓根目录 `VERSION` 与公开仓 tony-apan/maozhishi-skills 根目录 `VERSION` 里的仓库版本号。各模块自己的版本号只是标识，不用它判断更新。
- 怎么判定：公开仓版本号读不到（无网络，或公开仓没有 `VERSION` 文件）→ 用本地版继续、不要卡住，提一句没能检查更新。本地没有 `VERSION` 文件、或本地版本号读不出来 → 视为最旧版，公开版读得到就更新。公开版高于本地版 → 更新；两边一致 → 直接开工；本地高于公开版 → 不替换、只提一句（说清本地与公开各是哪个版本）。
- 更新怎么做：先备份、再替换。备份把将被替换的文件整份拷到本地仓根目录下的 `backup/<旧版本号或日期>/`，重名时加序号或时间后缀、不许覆盖已有备份，至少保留最近两份。替换只动仓里既有的技能文件（两个模块文件夹、`VERSION`、版本说明、模块地图、README 等）；**workspace-template 是用户数据区：里面已经填写的内容一律跳过、不覆盖，模板出了新文件只把新文件补进去**；用户自加、自改的任何文件不覆盖、不删除。清单里的受管文件即使被用户改过也照常替换，改过的旧版进备份、报告里点名；『不覆盖、不删除』只管清单之外的文件。若本地只有单个模块、没有仓根目录：先把公开仓整仓拉到与该模块同级处，作为以后的比对副本（原模块文件夹也按受管文件处理：先备份、再换成公开仓的最新版），并在报告里说明已补齐整仓。
- 换完之后：一句话报告——更新到了哪个仓库版本、用户资料现在在哪、是否完好；然后重新读一遍新版说明书，再继续开工。

### 新号开工顺序（新用户第一次用，按这个顺序走，不要跳步）

- 第一步：确认有没有 LaiCMS 账号，没有就按《联系说明.md》的官方入口开通，开通后再继续。
- 第二步：走安全录入卡四步把密码存进密码库，并试登录一次确认能进后台。
- 第三步：建本地工作区七层文件夹和每层索引。仓里随附的 `workspace-template/` 就是这套七层结构的现成模板（用户数据区，含每层索引的样子），照着它在用户本地建，不要另起一套结构。
- 第四步：检查并设置 Muse 邮箱、绑常用邮箱（见本节 Muse 邮箱部分）。
- 第五步：定两个「地」，当场分清、不要混成一件事。① 文章存档地：只存每篇文章的 Markdown 原稿，二选一——他的 Google 云盘文章存档文件夹，或他 GitHub 仓里的文章目录；选 GitHub 时才需要在这一步绑 GitHub，选云盘就不为存档绑 GitHub，不许因为选了云盘还让他绑 GitHub。② 全量工作备份地：存整个工作区的全量备份（底稿、清单、台账、发布记录、交接文件这些），默认推荐他本人名下的专属私有 GitHub 仓，他没有 GitHub、访问不稳或不愿意，就用 Google 云盘文件夹作备份地，也可以先不设备份地、只留本地（要跟他讲清账号丢失就没法无缝迁移的风险）。两个地可以是同一个 GitHub 仓，也可以一个云盘一个 GitHub，各走各的授权，第十节的同步与迁移按选定的备份地执行（细节见本节「备份地与专属仓库」）。
- 第六步：按用户主用渠道绑一个主渠道（WhatsApp 扫码或邮箱授权，先绑一个，不要两个一起推）。
- 第七步：走新建网站全流程，其中询盘表单的通知邮箱设为他的 Muse 邮箱，这样新询盘能进提醒链。
- 第八步：收尾绑 Google 账号、做 GA4 与站长后台关联、建 Google 表格台账。
- 第九步：问要不要开每日更新，点头后再建每日任务。
- 第十步：问一句要不要装可选增强 huashu-design（见本节「可选增强」），他点头才装，不装不影响任何流程，不要默认替他装。

### 定网站风格（开工必选，默认外贸 B 端）

- 开工时让用户在两种网站风格里选一个，随公司资料一起问清、最晚在定内容清单之前定下：① **外贸 B 端**（默认轨）——卖给海外批发买手、采购商与经销商，专业可信、参数与合作条款（起订量、样品、交期、定制、付款与物流）前置；② **跨境 C 端**——卖给海外个人消费者，场景种草、单品卖点与体验文案前置。问的时候用人话讲清区别（你的客户主要是批发商，还是个人消费者），不要甩术语。
- 用户没明确选、或说都行时，按默认轨外贸 B 端走，并明示一句「先按外贸 B 端做，想改随时说」——默认不等于不问，问过没选才落默认；维护老站时交接里没有风格记录的，首次维护先补问一次，用户不答就按默认轨并在交接里显名「未选、按默认轨」。
- 选择结果当场记进 site-brief 与交接文件（风格轨、选定日期、谁定的），后续视觉选色、产品呈现、文章选题、CTA 与美观评审全部以这一轨为准，两轨逐项对照见 references/laicms-风格档案.md，一站不许两轨混搭。
- 中途改选可以，但不是改一句话的事：改选后全站按新轨逐页复核（对照风格档案八项：视觉、Hero、产品呈现、文案语气、文章口径、CTA、信任元素、页脚逐项改齐），复核清单与结果记进交接，复核没走完不算切换完成。

### 可选增强：huashu-design（问过才装，永不默认）

- 这是第三方设计 skill（花叔出品），只在用户可能用得上深度设计时提一次：做页面原型、探索版式方向、做图与幻灯片这类超出建站日常的活。提的时候一次讲清三件事：它是第三方的；官方仓地址是 https://github.com/alchaincyf/huashu-design ；装不装都不影响建站与美观评审（没装时评审走随仓细则 references/beauty-review.md，口径一致）。
- 他点头后才引导安装，装完当场验证一次（能调用它做一次评审即算装好），结果记进交接文件；他说不装就不再反复提，等他自己问起深度设计时再提一次。
- 不许静默自动安装，不许用非官方来源的副本。

### 先确认后台账号

- 开工先问用户有没有 LaiCMS 网站后台账号，后台地址是 workspace.laicms.com。

- 有账号时，按四步引导用户把密码存进 Muse 设置里的密码库，全程说清每一步，第一步你发一张安全录入卡给用户，第二步提醒他只在卡里填账号和密码，填的内容直接进密码库，你看不到也不要让他发到聊天里，第三步他填完回你一句好了，第四步你再用密码库里的登录去开后台。

- 存密码这件事要跟用户讲明三句话，密码存在 Muse 的密码设置里不在聊天记录里、以后每次登录自动用不用他反复给、他随时能在设置里改或删。

- 登录被拒时不要反复试，先请用户在安全录入卡里重填一次，仍不行就引导他走后台的找回密码，改好后在录入卡里更新，不要在聊天里问他的新密码。

- 账号引导按三路走，先分清这个平台是哪一路，不要把三路混成一套：① 授权页登录（OAuth）——GitHub、Gmail、Outlook、Google、Notion、Facebook 等，用户本人在授权页登录确认，你不收密码，先核对授权的是哪个账号、哪个工作空间、给了哪些权限；② 扫码登录——WhatsApp 网页版，用户用手机扫码，扫好后确认能看到会话列表，并告诉他随时能在手机的已关联设备里退出；③ 密码库——只有 LaiCMS 这类只有账号密码的后台，才走安全录入卡四步存密码库。每一路开始前先核验当前环境里这项能力真的可用、授权范围够不够；能力不可用、权限不足或登录中途断了，就停在那一步，把缺什么用人话告诉用户，给他两条路：由他本人接管完成这一步，或换一条替代路线（如本地邮件客户端改走云端授权或网页版），不要硬承诺未验证的能力，也不要反复重试。

- 密码存好后，用 `browser.browse` 打开后台登录，用密码库里的登录完成登录，再看工作区里的站点列表确认登录成功，只记录账号标识，不记录密码。

- 没有账号时停下建站，把随仓发布的《联系说明.md》里的官方开通入口发给用户（入口以该文件为准，你不要自己编造渠道、电话或链接）；用户开通并把密码存进密码库后，再回来继续。

- 用户连这个平台都没听过、第一次想建站时，同样先把官方联系方式推给他：AllinCMS 官网页面上有官方微信二维码，发给用户让他扫码联系官方开通，并说清扫码后找谁、办什么。联系方式只能从官网现行页面当场核对后取（打开官网确认二维码与联系说明还是当前版本再发），不许用旧截图、旧文件或记忆里的号码；《联系说明.md》里要记下官网来源地址与核对日期，过期先重核再发。来发信等其他模块遇到没账号、没听过平台的用户，同一口径：推该平台官网的官方联系方式，不推私人联系方式。

### GitHub 绑定

- 用户选了文章存档到 GitHub 或要用仓库拉 skill 更新时，引导他在 Muse 的设置里绑定 GitHub，走 GitHub 授权页由他本人登录确认，不要让他把 GitHub 密码发给你，绑好后先读一下他的仓库列表确认绑定生效再往下走。

- [LaiCMS 后台](https://workspace.laicms.com) 是建站施工入口，用密码库登录操作。

### Muse 邮箱先设置好

- 开工时检查一下用户有没有设置 Muse 的专用邮箱，也就是他的 muse.ai 地址，没有就引导他走设置里的建邮箱卡片创建，地址由他本人看过确认，不要替他随便定。

- 创建时根据他的昵称和公司名，先给他两三个邮箱地址候选让他挑，比如只用他的昵称、只用公司名的缩写、或者昵称加公司名的组合，并讲清规则，地址只能用小写字母、数字和连字符，定下来之后不能改，让他选定再创建，不要替他拍板，显示名建议用昵称加公司名的组合，收件人一眼就知道是谁。

- 再引导他把自己的常用邮箱在 Muse 邮箱设置里验证绑定，优先推荐绑那个绑了微信的 QQ 邮箱，并提醒他打开微信里的新邮件提醒，这样邮件到了微信上就能看见。

- 跟用户说清这个邮箱的用途，新询盘的即时提醒和每天的日报，都从 Muse 邮箱发到他绑定的常用邮箱里，他不用守着电脑，在微信上第一时间就能看到。

### 备份地与专属仓库（默认推荐，可拒绝）

- 默认推荐给每位用户建一个他本人名下的专属私有 GitHub 仓库（每位用户一个仓）作全量工作备份地，在开工顺序第五步就跟他商量定下来：经他点头后在设置里走授权绑定，建完读回确认仓库可见性确实是私有，并跟他讲清第十节的同步与迁移安排，不要等账号出事了才补。但这只是默认推荐、不是标配必建——他没有 GitHub 账号、访问 GitHub 不稳或者不愿意，就改用 Google 云盘文件夹作备份地；他两个都不想用，就先只留本地真源，把「没有异地备份、账号丢失无法无缝迁移」的风险讲清并记进交接文件，不要卡住开工。两个地的分工要跟用户说清，别让他以为选了一个就被迫绑另一个：文章存档地只放文章 Markdown 原稿（见第三节），全量备份地放整个工作区的全量备份；备份只同步到他选定的那一个备份地，不默认往云盘和 GitHub 两个云各传一份，要双份备份须他另行点头。第十节的同步与迁移一律按他选定的备份地（GitHub 仓或 Google 云盘）执行；没设备份地时第十节的同步跳过，迁移只能靠本地文件夹搬运。

## 三、本地真源与工作区结构

- 所有资料的唯一可写真源是用户本地工作区文件夹（下称本地真源），开工时先建好，后面收的资料、写的底稿、记的进度都往这里放，不要散在聊天记录里。文章原稿的主本也在本地真源的 40 产出层，文章存档地（开工第五步二选一选定的那一处）里的那份只是存档副本，改文章先改本地主本、再同步到存档和站上，三处不一致时以本地主本为准。注意存档地与第十节的全量备份地是两个概念、不要混：存档地只放文章原稿，备份地放全量工作备份。

- 离线与关机分支（不许硬承诺无人值守）：每次任务开始先检查本地真源能不能打开、能不能写。用户电脑关机、本地真源打不开或没有写权限时，当天任务停写，只做能做的只读检查——注意这时交接文件也在真源里、同样写不进去，不要写「记进交接文件」这种当下做不到的动作。离线时只做两件事：① 只报状态——通过 Muse 对话或 Muse 邮箱给用户发一条状态通知，说清因离线暂停、缺了哪几项、等恢复后补；② 要记的事项先进临时队列——队列只放在经用户事先授权的一处可写位置（开工时定的那一个备份地里的临时队列文件，或用 Muse 邮箱留一份队列备忘），没事先授权就不建队列、只发状态通知，事项靠通知记录兜底。不要在真源不可达时还承诺文章已发、数据已记。设备恢复后先合并再对账：先把临时队列里的事项逐条并回本地交接文件、标清来源与时间，再把暂停期间站上实际状态、存档副本和本地主本逐项对一遍，有冲突先列给用户看再合并，补齐缺项、确认队列清空后，再恢复日常节奏。

- 工作区借鉴原工具包的骨架分七层，编号从 00 到 90，依次是收件、来源登记、知识底稿、任务清单、产出、数据、交接，每一层放一个索引文件，写清这层放什么、入口是哪个文件，找东西先看索引不靠翻。

- 站点基础信息、产品清单、文章清单和进度交接，全部存成本地 Markdown 文件，每层带索引，换了会话或者中途断了，照着索引和交接文件就能续上，不用凭记忆。

- 结构化清单以 Markdown 表格为主，人能直接打开看懂，产品多到表格不好维护时可以改用 TSV，只有机器程序要读的清单才用 JSON，不要为了显得专业全用 JSON。

- Google 表格只是每日数据的展示层，不是真源，数据先落到本地工作区，再同步到表格给用户看，表格哪天出问题，能从本地重建，不要反过来只把数据存在表格里。

- 文章的 Markdown 原稿存档地在新号开工顺序第五步就定好，二选一（在云盘与 GitHub 仓之间只选一处，不是两处都存）：存进他的 Google 云盘文章存档文件夹，或者同步到他的 GitHub 仓里的文章目录，文件名带日期和标题；选了云盘就不用为存档再绑 GitHub，选了 GitHub 就不用再往云盘存一份。站上内容与存档副本保持一致，改文章先改本地主本、再同步存档和站上（主本定法见本节第一条）。这里的存档地只管文章原稿，全量工作备份是另一回事、走第十节的备份地，两者不要混。

- 每轮工作都往 90 交接层的交接文件里记进度，中断后从交接文件续接，不凭记忆续做。

## 四、资料接入与产品事实底稿

### 收资料并一次确认

- 资料入口有三类，文件类收 PDF、PPT 和 Word，逐页读完提炼公司与产品事实，扫描版 PDF 没有文字层时先渲染成图再读，不要因为读不出文字就放弃。

- 借鉴类收友商网站链接，只借鉴对方的结构、栏目和呈现方式，文案和参数绝不照抄，站上内容只能从用户自己的资料里长出来。

- 口述类收用户直接说的信息，当场记进资料包，数字和联系方式这类关键项复述一遍让用户确认。

- 向用户收齐公司资料和产品资料，接受 PDF、文档、表格和图片，只用资料里有的事实，价格、证书、电话和 WhatsApp 这类资料里没有的一律不编造，缺的列进缺失清单问用户。

- 把资料提炼成一份 site-brief 和一份 manifest 内容清单，清单包含分类、产品、文章、页面、媒体图和站点设置，先整份给用户看，用户一次确认后再往后台写。site-brief 第一项记网站风格轨（见第二节「定网站风格」），清单确认时连风格一起让用户确认。

### 产品事实底稿（先有底稿才许上架）

- 每个产品上架前先做一份事实底稿，一件产品一张，写清产品名、客户平时的叫法、分类、型号、适合什么样的买家、用在什么场景、材质、关键规格、可选和定制、起订量、样品政策、交期、包装、认证和测试、贸易条款、和同类比不一样在哪、证据材料、客户常问的问题，还有一栏专门写禁止写和没证实的说法。服务类用户把实物字段换成服务说法：型号、材质、起订量、包装这类不适用的直接标「不适用」，改填服务内容、服务流程、交付方式、服务范围、案例与成果（只写已确认的）；单品或单项服务就只做这一张底稿，不为凑数拆假产品。

- 底稿里每个值都标状态，是已确认、是推断、是缺失还是和别的资料冲突，缺的先问用户补，冲突的先让他拍板，没有这张底稿不许往后台填。

## 五、建站施工

### 新建网站全流程

- 整个流程按下面顺序走，每一步都有过关标准，标准不过就停在这一步修好再往下，不带着问题往下滚，每步做完把产物和状态记进交接文件，中断了能照着续。

- 第一步开工摸底，登录后台先只读看一遍，站点列表、新建表单、产品、文章和页面编辑页的字段与上限都看清，后台改版会让老经验失效，先摸清再动手，过关是字段现状记进交接文件。

- 第二步定内容基线，先分清用户是实物产品、服务项目还是两者混合，再按已确认的清单定各类要建的数量。实物产品多时可参考产品至少 3 个、文章至少 4 篇的经验值，但这不是硬关卡：服务商、SOHO 或单品用户有几个就建几个，以用户点头的清单为准，不许为了凑数编内容，也不得因为数量少就停工。内容少时按美化小节的降级办法处理（删空模块、改网格列数）。文章主题、分类和标签一次列全，过关是数量和清单用户都确认过，后面终验按这个数对账。

- 第三步只建空站，在后台新建网站，名称 2 到 50 个字符加一句描述，建完回列表确认新站就是刚建的那个，记下默认网址，再把产品名和分类名列出来互相对一遍，不许重名撞名，过关是空站建好且名字清单无冲突。

- 第四步列改造清单，把新站模板里要换的值逐项列出来，品牌、联系方式、导航、页面文案、表单都在内，每项写上这个客户的值，还没有的显式标待提供，不留含糊的空格，过关是每一项有值或有标记。

- 第五步媒体先行，图片先处理好再集中传进媒体库，传完逐张补好标题和说明并对账，过关是媒体库里的张数和清单一致，细则看传产品小节。

- 第六步建基础分类和标签，产品和文章分开建，先看列表里已经有的，缺哪个建哪个，建完回列表确认都在，过关是分类标签和清单一一对上。注意顺序以本节为准：基础分类和媒体先行，小样之后再批量，不存在先把全部产品文章做完才做小样这回事。

- 第七步先做双小样：先上 1 个产品和 1 篇文章，发布后到前台核对并请用户验收（细则看小样先行小节）；用户点头后才批量其余产品和文章，批量做完再做全量关联检查（相关推荐、内链、首页模块），过关是每个产品都过四连验收、总数和基线一致，细则看传产品小节。文章批量完成后只进入第八步做文章侧与站内入口补齐，不在第八步重写或重发。

- 第八步是第七步批量文章的文章侧与站内入口补齐，不是第二次批量发文：只处理第七步清单中尚未完成的文章及入口事项，已经在第七步按写文章小节写、审、发的文章不再重写或重发；本步核对未完成项，补导航文章入口、首页精选文章模块，再逐篇打开前台确认，过关是每篇前台能打开、正文在。

- 第九步做页面与品牌，按美化小节把 7 个页面逐页做完；头部和页脚是全站全局块（2026-11-13 后台实测：主题设计器里 Header/Footer 为全局块，改一处全站生效），改完抽查两页确认生效，过关是逐页看下来和改造清单对得上。

- 第十步设首页并验主入口，把首页设在所有页面都做完之后，设完打开网站根网址确认看到的是真首页不是报错页，再把首页、产品、文章、联系四个主入口逐个打开，过关是四个都正常。

- 第十一步清演示，先列演示内容清单给用户确认再删，删完再数一遍产品、文章和分类，和基线一致才算完，中途要是重建过主题，演示内容会被重新带回来，要再清一遍。

- 第十二步终验交付，按发布终验小节逐项查，再交链接清单和测试清单，过关是链接清单逐条能打开、数字和基线对得上。

- 域名放最后，网站做到用户满意后才谈绑域名，绑完要在浏览器里实际打开验过才算数，平台显示的状态可能滞后，以实际打开的结果为准。

### 建后收口：全站检查、清理、审查、升级完善

网站建完不是交付完，终验之后固定走这四步收口，四步没走完不算交付：

- **全站检查**：全站每个页面逐页打开，不抽查——页眉页脚品牌与联系方式全站一致、导航每个入口点通、每页正文非空、没有空模块、破图和占位文案、产品与文章数量和内容基线对得上账、站内链接（内链、相关推荐、行动入口）逐个点通。检查结果逐页记进交接文件。
- **清理**：演示内容（演示产品、文章、分类、假评价、假新闻、演示号码与悬浮钮）清零，空模块删掉或按降级办法处理，失效与错误链接清除，重复内容合并。清理清单先列给用户确认再删（沿用删前确认口径），删完复数一遍和基线对账。
- **审查**：两审并行——内容审查（事实与禁编造、标题、摘要与搜索字段一致（按后台实有字段）、内链与行动阶段对位）和美观评审关（六维逐页打分，口径见美化小节），任一审不过不交付，问题逐项改完复审。
- **升级完善**：收口发现的问题分三类处理——站内问题当场修并复审；平台改不了的登记为平台边界，不硬磕；规范层面的教训（流程缺口、口径冲突、新实测值）回写交接文件并提规范修订，修订经审后递增版本发布，让下一个站直接受益。此后转入第八节巡检常态化，巡检每发现一类新问题，就重复这四步的小循环。

### 施工通则

- 新建站点时先实测后台表单，新后台创建表单只有名称和描述，名称 2 到 50 个字符，域名在建完后进站点里绑。

- 施工阶段只有一个顺序，以新建网站全流程为准：开工摸底、定基线、建空站、列改造清单、媒体与基础分类先行、双小样（1 产品加 1 篇文章）、用户确认、批量产品与文章、全量关联、页面与首页、清演示、终验。不要再用其他顺序表述。

- 分清内容类型的字段，产品、文章、页面和媒体的字段不能混用，换新站或后台变版后先重新核实字段再写。

- 记住保存不等于发布，每条内容都要保存后再发布，前台没更新先查发布状态，不要重复创建。

- 图片先处理再上传，产品图优先用白底方形图，图片转 WebP 且单张不超过 500KB（此数出自原工具包公开文档）；产品图的具体像素尺寸、横幅图尺寸和横幅体积上限原工具包查无出处，不写死，第一次在后台实测确认后记进交接文件，后续按实测值执行。图片必须传进后台媒体库，不要只贴外部链接；实在无图时可用图片 URL 临时验证流程，但须显名记为临时——外链图有加载延迟与失效风险，前台验图要刷新复核一次，正式内容发布前换成自有图进媒体库（2026-11-13 改造试跑实测：新站媒体库为空、无自带图库，补图只有上传与 URL 两条路）。文章封面尺寸同样首次实测后记进交接文件。

- 字段上限只认有出处的：文章摘要 200 字符是当前后台界面的实测约束，换一个站或后台改版后先复核再用，不要当成所有站都一样的死规矩。产品描述的字符上限原工具包查无出处（原库的 500 字符是媒体说明文字的上限，不要张冠李戴到产品描述），第一次填时在后台实测确认后记进交接文件。（2026-11-13 冷跑实测：当前部署产品编辑器描述字段显示 0/500 上限，按 500 执行、换站复核。）其他字段超限先压缩再填，不要等系统截断。

- 输入优先用粘贴，不要逐字打，Slug 逐字打会被吞掉连字符，富文本里打 @ 和斜杠会弹菜单，出现灰色自动补全残影时按 Esc 取消再继续。

### 小样先行再批量

- 先上 1 个产品和 1 篇文章做小样，发布后到前台逐项核对链接、封面、正文和状态，再把小样链接给用户验收样式。

- 用户验收通过后才批量其余内容，批量时每条做完都在前台读回验证，接口返回成功或保存成功都不算完成证据。

- 发布批准的口径在这里说清（这是对原工具包逐条点头红线的有意调整，要显式执行）：用户确认过的内容清单，就是对清单内各条上传和发布的批准，可以按清单批量做；清单外新增的内容、覆盖已有内容、删除任何内容，仍要逐条列出等他点头。每日更新的发布额度不写死在这一条里——只认第八节发文节奏小节里的那份有效授权记录（每日数量、生效日、选题范围），每日任务按当日获批额度发，超出额度的同样要先问；授权记录怎么建、提量后怎么改，见第八节。

- 平台自带的演示内容等小样通过后再清，删演示产品、演示文章和演示分类前要拿到用户在当前任务里的明确同意，能删的直接删，删不掉的列出来报用户。

### 传产品的细则

- 产品呈现按所选风格轨（见第二节「定网站风格」与 references/laicms-风格档案.md「产品呈现」）：B 端轨参数与批发条款前置、模板无价格位；C 端轨场景与单品卖点前置，价格只许按档案口径用真实价格作展示——平台详情模板没有价格与购买区块、没有购物车，两轨都不许假装有。

- 产品名用买家的话加关键规格写，让人一眼知道是什么、多大本事，不要只写内部型号。

- 链接名用小写加连字符，不带时间戳，开工前先和分类名、标签名对一遍，同名会在发布时才报错，提前避开。

- 产品排序一次规划好，序号决定列表和首页的展示顺序，不要东一个西一个随手填。

- 规格表每条的值控制在 200 个字符以内，长长的型号清单不要塞进规格表，放正文里写。

- 专业口径再加三条：规格数值必须带单位，单位用买家市场通行制式（公制与英制并标，如 mm/inch、kg/lb，只标一种时标目标市场的那种）；参数名用行业通行说法，不用厂内土话和内部编号当参数名；同一数值在规格表、正文、图片说明三处必须一致，对不上以事实底稿为准并当场改齐。

- 正文不能空，空正文的产品页只有图和规格表，是明确的事故，正文按适用场景、构造与规格怎么对应应用、选型要点、一个有边界的行动段来写，选型小提示用普通段落写，不用引用块。

- 禁编造在产品上再强调一遍，价格、起订量、认证、案例、销量、客户评价、交期、回复速度，没有来源一律不写。

- 图片先转成 WebP 再传，体积能小一大截，超过 500KB 的先压再传，不合格不许上，图片型资料里的图从原文件里裁出来，裁完逐张看一遍，去掉标题字和边角残留，不外找占位图凑数。

- 图传进媒体库后要逐张补好标题和说明文字，上传时顺手填的经常不生效，以媒体库里能看到的为准，补完再复核一遍。

- 图片逐张对账，以媒体库的实际记录为准，不信上传完跳出来的提示，张数、对应关系都对上了再往下，同一个页面里不要重复用同一张图，每张图的来源是客户自有还是外部授权都登记下来。

- 分类和标签分开建，产品分类、产品标签、文章分类、文章标签不能混，先看后台已有的，对账后缺哪个建哪个，建完回列表确认。

- 某个分类下面新建产品反复失败，或者建出来变成没有标题的草稿，先换一个已经验证能用的分类把产品建成功，再改回正确分类，不要对着一个分类死磕。

- 每个产品做完过四连验收，列表里数量、名称、链接名、规格逐条对，正文打开非空，状态是已发布，前台详情页打开有正文段落、事实内容在、相关产品链接能点且没有空着的模块，四样都过才算这件完成。只有一个产品时相关推荐必然为空，这一条改判为：已按美化小节删掉相关推荐模块或补到至少两个条目后再验收，不拿必然为空的模块卡住单品用户；全量关联检查放到批量完成后统一做，不压在首件小样上。

- 改老产品时先打开看它现在的样子，以现在的值为准再改，不要拿一份旧稿整份覆盖回去，旧稿里空着的字段会把后台现有的内容清掉。

### 写文章的细则

- **选题与行文按目标客户痛点走**（Tony 2026-11-14 定版）：文章选题先对准目标客户的采购痛点——交期、起订量、品控、合规、利润空间等，写客户在采购决策里真会卡住的问题，不写与采购决策无关的泛科普。
- 文章按所选风格轨分流（见 references/laicms-风格档案.md「文章选题与行文」）：上一条采购痛点是 B 端轨口径；C 端轨改按消费场景与使用痛点选题行文（怎么选、怎么用、用在哪、怎么保养）。两轨共用同一套选题验证、痛点证据与篇幅深度闸，事实只用底稿、不许编造，这一条不分轨。
- 每篇动笔前先定一份选题约定，写清客户真正会搜的那个主词、同义的其他说法、要排除的词、这篇帮客户解决什么事、客户现在处在了解、排查、比较、验证、购买的哪一步，没定好不许写。

- 定选题要看四种证据，分开记，客户是不是真有这个决策，看聊天、询盘和销售记录，这个词是不是真有人搜，目标市场有没有需求信号，搜这个词出来的页面现在流行哪种形态，清单、对比、指南还是案例，缺哪种就标缺，不拿推断冒充证据。

- 文章形态跟着搜索结果走，那边流行对比就写对比，流行清单就写成能照着做的清单，不把所有题都写成一篇泛泛的长指南。

- 主词里带购买、价格、报价、供应商、起订量、交期这类交易词的，这篇就是交易型内容，归到购买阶段去承接，不要包装成纯科普，不是购买阶段的文章，标题里不许出现这些交易词。

- 一篇文章只干一件主任务，次要问题用链接交给别的页面，开写前先把全站已有文章盘一遍，同主题已经有的就合并或改写，不新开一篇和自己抢。

- 客户的原话只是选题假设，先按原话、场景、痛点、想要的结果、顾虑、决策约束提炼成条，再用站内搜索、站长后台数据或关键词工具里至少一种交叉验证过，才能当真搜索词用。

- 痛点按六个节点写满，谁在疼、什么工作场景触发、缺哪份证据所以没法判断、这个缺口怎么变成复测、追问、返工或等待、对项目造成什么有边界的后果、读者看完这篇能做出什么决定或止损，六格缺一格、或者把后果写成没证据的确定损失，都算不合格。

- 痛点没有证据时用可能、会带来风险这类有边界的话说，不编停线成本、返工比例、收益数字和客户原话。

- 篇幅按文章形态给带（英文词数，是经验带不是凑数指标）：指南型 1200–2000 词、对比型 1000–1800 词、清单型 900–1600 词、诊断排查型 800–1400 词、案例型 800–1200 词；中文站按字数计。**实际下限＝max(篇幅带下限, 正文深度地板)**：深度地板是硬闸（文章英文 ≥1,200 词、中文 ≥2,000 字，见《交付硬闸增补》正文深度下限），带下限低于地板的形态（如诊断排查型 800 词、案例型 800 词）按地板执行，篇幅带只在地板之上的空间里起经验指导作用；英文词数与中文字数是两套并行口径、不互相换算，不要再拿 1.8 倍之类的系数互推。下限是把一个问题讲透的最短长度，低于下限多半是没讲透；超上限先拆篇或合并选题，不注水、不换个说法重复凑长度，防空洞自检不过的段落删掉不留。

- 正文结构全篇只有一套，不要再套第二套顺序：先是首屏答案区（在正文五段之外），再是正文五段。五段顺序是钩子、诊断、决定、避险、下一步动作：钩子用客户看得见的失败或触发场景开场，然后诊断原因和证据缺口，然后给现在能做的决定，然后说清假设、不适用的情形和验证边界，最后给一个有边界的下一步动作。五段可以合并相邻的，但不能调顺序、不能漏、不能把最后的行动提前变成推销。

- 「场景代入、痛点、代价、原因反转、方案」不是另一套顺序，只是写钩子和诊断两段时的写法：代价要用细节不用形容词，方案里的数字全带来源；「按不同人给不同选择」写在决定段里，收尾和行动引导就是第五段，不要另起一套骨架和五段打架。

- 写出代入感靠三件事，用第二人称说话、给具体的时间物件和数字、写冲突的细节，每段至少占一件，每段只讲一个意思，段和段之间有过渡句。

- 首屏先给答案（正文五段之外的答案区）：第一个小标题出现之前，用 2 到 4 句先把直接答案说清——做什么、要什么证据、适合谁、预期得到什么——紧跟一句钩子场景带入痛点，再各用一句话写清适合谁和不适合谁，不许用公司介绍和行业大词开场。

- 层级守规矩，页面本身只有一个大标题，正文从二级标题开始不跳级，加粗只给真正的判断、证据缺口、止损条件和下一步动作，不给产品名和栏目标签乱加粗。

- 标题与搜索口径按后台实测字段执行（原补记 17 并入）：文章编辑器当前只有标题与摘要两个字段，没有独立的搜索标题、搜索描述字段，也没有文章分类字段——不要按「四个搜索字段＋分类先行」的想象去找不存在的字段。文章按标题、摘要与前台显示三处同一套值、逐字一致执行；产品侧有独立搜索字段的（搜索标题、搜索描述），与页面大标题、摘要写同一套值。草稿、定稿、发布三个地方逐字一致，出现第二套值就是不合格。

- 发布前逐项过一遍搜索快查，标题 60 个字符以内、写成页面名加品牌的形式、全站不重复，描述 150 到 160 个字符（这是英文字符口径，中文站的描述长度另按后台实测在交接文件里定）、按要办的事加证据加下一步来写且不超后台 200 的上限，链接名短、可读、连字符分隔、没有时间戳和中文，每张图都有说明文字，正文里没有模板词和空着的占位文案。

- 平台定死的东西要分清，像标题的拼接方式这类后台改不了的，登记为平台边界，不当成站内待修问题反复折腾，后台能改的描述、摘要、图片说明、链接名和发布状态，每一样都认真改到位。

- 内链按作用挂，不按数量凑，每条链接都要说清买家点过去能完成什么事，锚文本写清这件事，不用点这里、了解更多这类只催着点的话。

- 内链按阶段配，了解阶段至少链一篇知识文章或栏目页，排查阶段至少链一篇诊断或支持页，比较阶段必须链对比页，有证据才链产品页，验证阶段必须链技术核对页，购买阶段至少链产品页加一个真实询盘入口，目标页不存在的链接不许挂。

- 内链要落到页面模块上，正文里贴的链接在前台可能显示不出来，链接挂到相关推荐、产品展示、文章页行动块这些模块上，不要在正文里假装挂好了。

- 行动引导按阶段分级，了解阶段只做页内自检、不收联系方式，排查阶段留症状和环境信息转人工，比较阶段用页内工具或动作、默认不收联系方式，验证阶段走两轮渐进，购买阶段才收完整的询盘信息，包括买什么、数量、目标市场、时间、贸易条件和必要的技术信息。

- 验证阶段的两轮要分清，第一轮只收 4 到 6 个最关键的问题，只回三样东西，资料齐不齐、缺哪些证据、下一步做什么，第二轮才收细化信息，而且每一项都要标明它改变了哪个判断，两轮收齐、再经一位具名的技术负责人实际看过，才可以给可以选或就此打住的结论，第一轮就下结论算违规。

- 技术上合格不等于销售上接受，技术合格要靠完整证据加负责人确认，不能表单一交就自动算数，销售接受是另一道商业确认，两件事不能互相冒充。

- 每篇都要备三种行动面，一个主要的、一个低门槛的比如先自检或先备资料、一个发不出去时的退路比如把资料包存本地再单独给一条验证过的联系路径，入口点了没反应的假表单和假链接不许摆。

- 行动引导的文案写收益句，写比一比参数、帮你选型这类说清好处的话，不写光秃秃的了解更多和获取报价，而且放在讲清判断方法之后，不抢在前面。

- 写作走流水线，先从资料里提炼事实，再列骨架，再成稿，然后换一个没参与写作的视角通读评审，按代入感、钩子、层次、空洞度、格式、痛点命中六项挑问题，点名最弱的三处并给改法；其中痛点命中单独卡：痛点必须有证据来源（渠道提炼、询盘记录或销售记录，写清出处），钩子与诊断两段要让目标客户一眼认出「说的就是我」，凭空想的痛点、换个行业也成立的万能痛点算不命中，整篇打回重定选题，评审不过只改表达不动事实，改完再审。

- 定稿就是锁定，定稿之后改任何一个字，都要重新过一遍评审，不要改完直接发。

- 发布后补三件收尾，导航里加回文章入口、首页恢复精选文章模块、逐篇打开前台确认能打开并且正文在，发布动作做完不等于文章这件事做完。

- 正文格式守红线，只用段落和二级、三级标题，正文不用引用块，不排表格和列表，前台会把它们铺平，对照信息写成文字对照行，图只放封面和页面模块，正文里不插图，草稿里的格式符号不要残留到正文里。

- 常见问题不是每篇必配，只有问题有真实证据、答案能改变客户决定时才加。

- 效果不许承诺，标题、描述、正文和行动引导里都不许出现保证排名、保证流量、保证询盘这类话，效果等有了站长后台和客户数据、过了观察期再谈。

- 交稿前做一遍防空洞自检，逐段问删掉这段读者损失什么、有没有具体的名词数字和场景、每段有没有落点，再查全篇是不是只有一个行动主题。

### 文章配图与做图规范

- 每篇文章必须有封面图，来源按这个优先级取：① 产品事实底稿里登记过的自有图（实拍、已授权）优先；② 站内已过审的自有图复用（同一张图不要在多篇文章里反复当封面）；③ 都没有时可以生成氛围/示意类配图，但不得冒充产品实拍，不得出现虚构的产品外观、参数和场景证据，生成图只作氛围与示意。外找的占位图、带水印的图库图一律不用。

- 做图按专业口径：构图留出安全区，主体有呼吸感，不把关键信息压在边缘；全站图片一套处理——同样的色调、圆角、边距与底色风格，不许一篇文章一个样；图上叠字只放一句钩子话，字数克制，字体与全站一致。

- 产品图只许真实：裁切、调色、去杂物可以，美化不得改变产品外观、颜色和结构；示意图与实拍同页出现时要分清并标明。

- 尺寸与体积按施工通则（WebP、单张 ≤500KB、尺寸按交接文件里的后台实测值），传进媒体库后补好说明文字；封面图同样过美观评审关的快速审（见美化小节）。

### 把网站做美观

- 首页模块以下面 11 个模块为准，本节其他地方不再另列一套必备模块清单；缺模块的首页先补结构再谈样式。

- 全站品牌只留用户自己一家，Logo、品牌名、页脚和联系邮箱统一，主题自带的演示品牌和假评价、假新闻、演示号码悬浮钮全部清掉。

- 产品图统一白底方形再上，封面和横幅尺寸按交接文件里记的后台实测值走，图片糊、变形和裁到标题的先重裁，不要凑合发布。

- 美化开工前先定一句视觉方向，默认走克制、安静、可靠的路子，信息优先不堆装饰，视觉是为看懂信息服务的，不许拿好看掩盖内容不足。
- **网站风格按开工选定的那一轨走**（选择机制见第二节「定网站风格」，Tony 2026-11-14 定版）：默认轨为外贸 B 端——面向海外批发买手与采购决策人，专业可信、参数与合作条款前置，忌 C 端消费风（生活方式种草、情绪化文案、零售促销话术）；用户选跨境 C 端时整站切 C 端轨，视觉、选色、图片与排版密度按 C 端轨执行。两轨逐项对照见 references/laicms-风格档案.md，施工一律按所选轨、不许两轨混搭；视觉方向句也要按轨写明（B 端轨默认克制、安静、可靠，C 端轨可鲜明、场景感强），记进交接。

- **美观评审关（每页必过，单独做的页面也不例外）**：每个页面（首页、关于、联系、产品列表、产品详情、文章列表、文章详情，以及任何单独制作的落地页）做完或改完，都要过一遍六维评审再交付——概念/立意、哲学一致性、视觉层级、细节执行、功能性、创新性，逐维打分并写一句判语。过关线：总评 ≥7 分且概念维 >5 分（概念 ≤5 时总评封顶 6 分，先修概念再谈执行）；不过关的按评审问题逐项改、改完复审，不许带着评审问题交付。环境里装了 huashu-design skill 的用它执行评审；没装的按随仓的评审细则（references/beauty-review.md）逐项打分，口径一致、零额外安装，不因没装就免审。文章封面与配图过快速审：只看视觉层级、细节执行、功能性三维，过关线同样 ≥7。评审结论记进交接文件（页面、日期、总分、最弱一项）。风格定位按所选轨评审（双轨判据见 references/beauty-review.md「风格定位（加审项）」）：选 B 端查 C 端残留、选 C 端查 B 端误入，串轨与混搭扣一致性。

- 平台能改与改不了的按实测分清（2026-11-13 后台设计功能盘点）：主题级能改的是整套颜色 token、圆角、全局间距基准、阴影、字体族（仅族名字符串）与字距；改不了的是字号（无标题与正文字号入口）、逐模块间距、页眉半透明（无开关）、自定义代码（无入口）、第二套主题（仅 1 套 Default、无主题市场）。美化先把能改的主题 token 用满，再靠内容、结构、选图、模块组合和文案做；其余登记为平台边界，不耗时间。

- 内容量影响美观：产品和文章多时网格和相关推荐才不显空；数量不够时宁可删掉相关模块、改网格列数或关掉筛选栏，也不硬凑假内容撑场面，服务商和单品用户同样按这个降级办法走，不卡数量关。

- 标准是 7 个页面各司其职，首页、关于、联系、产品列表、产品详情、文章列表、文章详情，缺哪个先补哪个，不要只美化首页三页就交差。

- 首页按买家动线排 11 个模块，顺序是主视觉轮播、分类卡、主推区、特性证明、精选产品、材质故事、客户评价、精选文章、常见问题、订阅、联系区（精选文章在前、常见问题在后，这个顺序出自原工具包的新站清单，不要调换），先让买家看懂卖什么，再给凭什么信，然后看产品、读内容，最后留询盘。服务商没有实物材质可讲时，把材质故事这一块换成服务流程或案例块，其余顺序不变。

- 客户评价模块只放真实评价，用户拿不出真实评价就删掉这一块，不要摆假评价撑门面。

- 关于页按介绍、公司故事、数字指标、价值观、团队、行动区的组合搭，数字指标只用资料里已确认的数字，没有的就不放这一块。

- 联系页按页头、联系信息卡、地图、询盘表单的组合搭，社交链接没有真实账号就明确留空，不要挂平台默认的假链接。

- 品牌替换有四件，逐件换，页眉换站名、标语、Logo、导航和头部按钮，导航的下拉要挂真实分类，页脚换品牌名、品牌描述、链接列、社交链接、版权，并清掉演示字样，询盘弹窗换标题和描述并绑站内真实表单，悬浮钮有真实号码才挂、没有就把这个元素整个删掉，留空会被平台顶回演示假号。

- 头部和页脚是全站全局块，改一处全站生效（旧「按页存」口径经 2026-11-13 后台实测作废）；改完抽查两页确认，再全站搜演示品牌名和模板词，结果必须是零。

- 后台设计功能实测要点（2026-11-13，Default 主题）：仅 1 套主题、无市场与复制导出；Logo 只在页眉模块里设（站点信息里只有站点图标 Favicon，两处不要混）；首页 15 个模块可开关、排序、改字段，列表页可改列数与每页条数；单页（关于/联系）同为模块拼装，没有整页富文本；产品详情模板没有价格与购买按钮区块（模板结构边界），购买引导靠正文行动段与页眉报价弹窗、联系模块承接，不许假装有价格区；站点语言默认英语且锁定，中文内容是在英语环境下填的，排版与字段口径按此预期。

- 设计器操作细则（2026-11-13 改造试跑实测）：① ACCENT 颜色 token 在 Default 模板的可见组件里基本不被引用，改它前台看不出变化；要可见变色须动 PRIMARY，但影响面大，先小样验证再全站发布，不要指望 Accent 做品牌色。② 改全局块（页眉、页脚、浮钮）保存与发布时会弹「全局更改确认」，逐项核对影响清单再确认；页面级模块隐藏不弹此确认。③ 图层面板选模块要点文字区，点拖动柄容易误选相邻模块。④ 品牌替换要逐模块搜模板品牌词：页眉页脚改完不等于清零，模块文案里仍可能残留（如引言里的模板团队名），验收按「全站搜演示品牌名结果为零」执行。⑤ **切换页面上下文会丢弃未保存的草稿**：设计器里每页改完立即保存并验证，再切换页面；各页（Home/About/Contact 等）独立保存与发布，发布状态条显示 Draft 不可信，以前台读回为准（2026-11-13 清理试跑实测：首轮整页改动因切换未保存全部丢失、逐项重做）。⑥ 导航菜单与分类是两套独立数据：删分类不清菜单，Header 菜单项（含嵌套）要单独清，删父菜单项后子项会上浮为独立项、须再删一次；分类名以后台实名为准（清单叫法可能与后台不同）。⑦ 首页分类展示模块的卡片自带分类名，删分类后卡片仍在，须改卡或隐藏模块。

### 演示品牌化冲分法（无真实品牌资料时把占位站升到演示水准）

适用：演示站、试跑站、教学站——没有用户真实品牌与产品资料、但要拿出能看的成品时用本法。正式站有真实资料时不用本法：品牌名、产品参数、图片一律以用户资料库为准（见共用底座资料库四格），产品图只许真实（见《文章配图与做图规范》）。本法的产物是「演示品牌」：姿态按真品牌做，资料是演示性质，交接里必须显名。

**第一步 品牌简报（五项先定死，写进交接再动手）**：① 品牌英文名（与模板演示品牌名不得形近）；② 品类一句话（卖什么）；③ 目标买家一句话（给谁、零售还是批发口径）；④ 主色一个（取深色系 oklch 值，与品类气质一致，如户外取松绿、工业取深蓝）；⑤ 主推产品档案（名称＋至少 3 个硬规格，数值带单位、公制英制双标＋2 个卖点，卖点写买家收益不写空话）。

**第二步 主色（先改色，后改文）**：改主题 token 的 PRIMARY，**不要改 ACCENT**——实测 ACCENT 在 Default 模板的可见组件中基本不被引用，改了前台看不见；PRIMARY 影响按钮、链接、徽章，全站生效。改前把 PRIMARY 原值记进交接（可回滚）；保存发布后全站扫一遍生效点（主按钮、链接、徽章类元素），逐页确认无漏网旧色。

**第三步 文案替换（按面逐项过，不留占位词）**：页眉品牌名与 Tagline → 轮播每张的 Eyebrow/Title/副文案 → 主推产品卡（SPOTLIGHT 类）→ 信任条（只写演示品牌能兑现的口径，不借模板的包邮退货承诺）→ 内容区引言 → 关于页 Hero 与品牌故事（按简报写 2–3 句真故事姿态）→ 联系区口径（演示站用站域名邮箱、不用私人真实联系方式）→ 页脚品牌描述与版权 → 示例产品改名并按产品档案补齐描述与规格表 → 示例文章标题与摘要向品类靠拢。验收口径：全站搜 Test、Trial、Lorem 与模板演示品牌词，结果为零（演示品牌自身的名称与品类词除外）。

**第四步 图片（生成图只限演示站）**：演示站的氛围图与演示产品图可用 AI 生成图，条件是同色系（与主色呼应）、一图一用途不复用、上传进站内媒体库再引用（不留外链临时图）；正式站产品图只许真实，生成图不得冒充产品实拍，此界不因本法放宽。生成提示词要点：写明品类、主色、场景与光线，全套图同一光线感；封面另过三维快速审（见《美观评审关》）。

**第五步 执行顺序与纪律**：简报 → 主色 → 图片上传 → 文案逐面替换 → 逐页保存发布（沿用设计器细则：每页改完立即保存再切换、全局块改动过确认、发布以前台读回为准）→ 全站关键词验收 → 复评。任一步卡住先记卡点，不跳步硬凑。

**第六步 评分预期（先说清天花板）**：本法典型增益为概念 +2、一致性 +1、细节 +1，总评约 +0.8～1.2；平台边界三项（页眉半透明、产品详情无购买区、字号不可调）不动，功能维封顶 6，终评落在 7.2–7.6 属正常，**不承诺 8 分以上**。复评仍按六维逐项出分，差在哪写哪。

**第七步 交接**：品牌简报五项、PRIMARY 原值、生成图原稿存档位置、复评分数与剩余边界，一并记入交接；后续真实品牌接手时，演示品牌整套替换、不与真实资料混用。

### 正文排版规范（标题有层次、逻辑看得见，2026-11-13 用户走查回落）

长文一墙到底是移动端第一劝退项。所有文章与产品正文必须满足：

- **标题层级**：正文用编辑器的标题样式分段（H2 作分段标题、每段一个），段内要点用加粗引导句起头；禁止把分段标题写进普通段落里与正文同字号同字重。
- **段长上限**：单段不超过约 120 个中文字（英文约 60 词），超了就拆段；连续三个长段之间必须有标题、列表或图片打断。
- **清单用列表**：步骤、检查项、规格要点一律用列表呈现，不写成逗号串成的长句。
- **首屏答案区**：独立成段、关键句加粗，读者不滚动就能拿到结论。
- **结尾 CTA 段**：每篇固定收尾——一句行动引导＋明确去向（产品相关文 → 产品页或询盘入口；知识文 → 相关产品页或联系页），与美化细节清单「单页也要有下一步」互锁，缺了不算交付。
- **移动端读回**：发布后用窄屏（手机宽度）读回一遍，标题与正文层级分明、不用放大能顺读，才算过排版关。

### B2B 合格站要素清单（像个正经外贸 B 端独立站，逐项验收）

- **CTA 落点表**（逐项在位才算合格）：页眉报价钮全站可见且可达表单；首页至少 3 处行动点（轮播按钮、主推产品卡、页尾联系区）；产品页正文有行动段（模板无购买区时的承接口径）；每篇文章结尾有 CTA 段；关于页结尾有下一步；页脚有可达联系方式。CTA 文案用买家语言（Get a Quote / Request Samples / Talk to Sales），不用空泛的 Learn More 占位。
- **信任要素**：公司一句话定位在首页与关于页一致；批发条款有处可查（起订量、样品、交期、定制四项，写在 FAQ 或关于页）；联系方式真实可达（邮箱与表单实测可提交）；响应时限明写。演示站用演示条款，交接里显名，正式站换用户真实条款。
- **FAQ 必备五题**：起订量、样品政策、交期、定制（logo/包装）、付款与物流口径——B 端买家下单前必问的五件，缺题就是缺信任。
- **产品线门槛**：合格演示至少 3 个产品、分类可逛、导航能按分类进；单产品站概念与功能都压分（与《演示品牌化冲分法》衔接）。
- **验收方式**：以第一次来访的海外买家身份走一遍——30 秒内能答出「卖什么、起订多少、怎么联系」，答不出就改对应要素，不许用「内容都在页面上」搪塞。

### 发文规范增补（借鉴 allincms-content-ops 与 website-content-ops，2026-11-13 研读回落；与前文冲突处以本节为准）

来源：tony-apan/allincms-content-ops（风格指南与范文）与 tony-apan/website-content-ops 的 AllinCMS 文章操作适配器（下称 B 仓适配器，2026-07-27 有 11 篇全字段文章串行发布实证）。本节把可迁移口径并入本 skill，并对冲突口径作出裁定。

**一、发文元数据清单（每篇动笔前先立，缺项不发布）**：标题（≤60 字符、含主词）、链接名（kebab、全站唯一）、搜索意图一句话（读者要办的事）、主查询词 1 个＋长尾 3–5 个、差异点一句话（本篇比同题最强竞品强在哪，写不出不许写）、证据至少 1 项（数据、截图、实测记录，带出处可回核）、分类与标签（先取后台 ID 再填）、摘要（120–165 字符为搜索描述口径；后台摘要字段 UI 上限 200 字符是当前环境证据、不是平台契约）、封面 alt（<125 字符，同时写清图片内容与它支撑的论点）、内链计划（按阶段与目标逐条写理由，见第四条）。LaiCMS 后台没有 frontmatter，这张清单记在本地工作区该篇的记录里（见 §三目录），发布前逐项打勾。

**二、标题与开头（在《正文排版规范》之上加三条硬口径）**：① 每个 H2 必须对应一个买家异议或一条长尾查询，对应不上的小节删掉或合并——标题是意图映射，不是装饰；② 第一句直接回答主查询，禁「在当今……」「随着……的发展」类热身句，需要补充的 nuance 放第二句，第三句把读者导向对应小节；③ 有数字的论断必须有出处（底稿或公开来源），无证据的统计不许写，估算要显名。

**三、清单、表格与正文插图（冲突裁定，覆盖前文两处旧口径）**：① 清单与步骤用**有序列表**呈现（当前主题实测可正常渲染）；无序列表在当前主题会被渲染成嵌套 div（内容可见、语义打折），非用不可时接受并在交接记为主题表现缺口；复杂对照优先写文字对照行，简表可用但发布后要在前台核对没铺平。此条覆盖《写文章的细则》「不排表格和列表」与《正文排版规范》早期表述的冲突，以本条为准。② 正文插图分通道：走接口上传路线（见第六条）时可用正文插图，按 B 仓适配器的原位绑定与十项完成口径执行；走后台 UI 手工路线时维持「正文不插图、图只放封面与模块」的保守口径。③ 图片文件名用 kebab 且含主词（<60 字符），caption <30 词给结论；一个项目只用一个图床，不混用。

**四、内链与 CTA 版面纪律**：内链按文章阶段与目标逐条定，每条在元数据清单里写明理由（承接哪个异议、导向哪个下一步），无理由不凑数、可以为零但须记「不适用及原因」；每页从首页 ≤3 跳可达（结构可达性仍查）；一页只有一个主 CTA 且与搜索意图阶段对齐，CTA 动词必须具体（Get a Quote、Request Samples、Download the Spec Sheet），禁用 Learn More、Get Started 类空动词；次级 CTA 只在页尾出现一次，正文中段不弹窗。此条与《B2B 合格站要素清单》的 CTA 落点表互补：落点表管「有没有」，本条管「怎么摆」。

**五、残留词固定清单（草稿、预览、线上三处都要搜，命中即改）**：模板演示类——Northstar、buildnbuzz、555-0142、San Francisco、Free shipping、Shop new arrivals、Weekender、New season arrivals、Everyday essentials、WHY CUSTOMERS COME BACK、Shop materials、SHIPPING / RETURNS（作模板文案出现时）、coming soon、Lorem ipsum、images.unsplash.com（作正式图源出现时）；占位类——Test Storefront、Trial、试跑、测试（作内容措辞出现时）。清单随新发现增补，验收不再每轮临时想词。

**六、上传通道（推荐路径与降级路径）**：B 仓适配器证明 AllinCMS 文章可用「登录态浏览器内接口回放」上传（Markdown 转结构化节点、封面走媒体对象、分类标签用 ID、草稿与发布分步、发布后四层验收：后台状态＋列表页＋详情页＋DOM 内容）。执行环境支持脚本回放时（Codex/Claude Code＋浏览器通道类环境）优先走 tony-apan/website-content-ops 的现成适配器，并守其硬规：不模拟点击上传、不导出凭据、运行时合同（action ID 等）每次从当前部署重抓不写死、创建文章合同未捕获前不自动建新篇、状态不明不重发先对账。不支持脚本回放时走本 skill 原 UI 路径（逐字输入、发布三证），并知悉 UI 观察（slug 连字符被去掉、徽章滞后等）只是 UI 路径现象，不当平台契约引用。

**七、发布前审计留档**：每篇发布前留一份审计记录（记在交接或该篇记录里）：机检项（元数据清单打勾、残留词三处搜零、内链理由清单、meta 长度）＋异议清单。显名轻量裁定：源仓（allincms-content-ops 的 audits 口径）要求隔离审查者、至少五条异议与最低分门槛，本 skill 取轻量版——异议以五条为目标并逐条回应（接受/驳回附理由/延后），不足五条须显名原因；审计须含独立视角（独立审查者、隔离子代理或用户本人至少其一），自审只作预检、不单独构成发布审计。低风险改动（错字、单字段）可轻审；动正文、分类标签、封面、发布状态的按全审，改稿后按范围复审。

1. **正文不用列表节点**：母库 FORMAT-SPEC（2026-08-29，编辑器截图＋payload 证据＋6 轮实测）证明编号/无序列表在其部署的公网渲染为无语义文本平铺；但另一部署的格式验收记录里列表可用——证据是分部署的，不作全平台断言。本 skill 取保守默认：未实测当前部署前按「列表平铺」处理，v3.2.8「清单用有序列表」作废；清单改法：H2 标签段＋加粗引导句分条，编号写进文本（如「第一，先查……」）。若当前部署前台实测列表渲染正常，把结论与部署标识记交接后可启用、个案为准。
2. **正文不放内链节点、不插图（不分通道）**：内联 link 节点在其部署前台平铺无链接、image 节点平铺或异常（另一部署有内链与图片验收通过的记录，同为分部署证据）。保守默认：未实测当前部署前，内链与 CTA 一律由页面模块承接（feature-grid、product showcase、related、contact 模块），正文只用自然语言指路（如「规格全文见产品页」）。与列表同一出口：当前部署前台实测内链/图片渲染正常并留部署标识证据后，可个案启用。v3.2.8「接口路线可用正文插图」作废；接口路线的价值在结构化标题/段落与字段完整，不在正文嵌图。正文原生块在保守默认下只用段落、H2、H3、引文块四种（此为 FORMAT-SPEC 对应部署的口径，非全平台断言）；Markdown 记号（星号、方括号链接、井号标题）会被当纯文本显示，禁用；引文块只许有出处的真引文；数值单位带空格（750 ml、26.5 cm）。
3. **全局块分路径看（两种极端旧表述都作废）**：① UI 路径：页眉页脚是全局块，在任一页面上下文保存时会弹「全局更改确认」，确认后全站生效（2026-11-13 改造轮实测：改页眉页脚后三页前台读回一致）；但每个页面自身的模块改动仍须在该页上下文逐页保存并发布——全局块传播与页面级保存是两件事，不许混为一谈。② 接口路径：母库 ONEPASS 步骤 9 的按页 commit 是接口路线的行为，不外推到 UI。早期「按页存、逐页改」与 v3.2.9 的「改完必须逐页重交」都过头，以本条分路径口径为准。

**二、写文章增补**
1. **五阶段合同（先定阶段再动笔）**：Learn（只解释与自检，不收资、不用「了解更多」冒充 CTA）／Troubleshoot（先给排查，只有真实支持渠道才引导人工）／Compare（共同维度与不适用规则先于推荐，禁价格与起订词去勾非购买查询）／Validate（唯一允许两轮渐进收资的阶段：首轮 4–6 个最小决策输入，二轮每项须是新增或深化首轮并写明新增的决策目的）／Buy（独立询盘包：数量、目标市场、时间窗、贸易条件、技术输入）。文章的 CTA 与收资深度由阶段决定，不由作者临场发挥。
2. **决策五段与行文六段分工**：五段决策序列（钩子→诊断→决定→避险→行动）管买家决策推进，不得调序、不得把行动段提前成无证据推销；行文再按递进检查（认识→理解→判断→决定，术语先通俗化、CTA 只在决定段出现）。两套是同一篇的两个检查面，不冲突。
3. **首屏直答加强**：首个 H2 之前约 120–140 英文词（中文约 220–260 字，本地换算、非源实测）内除答案外，还要给适用边界（适合谁、不适合谁）与承诺边界（本文能帮你决定什么、不能代替什么）。演示/虚构内容须在首屏显名。
4. **加粗有角色**：正文加粗只给六类决策信息——条件、风险、证据、不适用、下一步、结论；产品名、人名、栏目标签不加粗，不整段加粗。
5. **FAQ 裁定（与 B2B 清单的调和）**：分两层：站级商业 FAQ 是站点模块（首页 FAQ 区），冷启动与演示站按《B2B 合格站要素清单》配齐买家必问五题（起订/样品/交期/定制/付款物流），内容须过事实与授权门槛（条款以用户确认为准）；文章级 FAQ 不是标配，只有搜索数据、询盘与客服记录里出现该文任务未承接的具体追问时才加，无触发不加、不复述正文凑数。
6. **评分双轨**：文章评审分开报结构分与证据分（结构齐不等于事实真）；演示稿的证据分只记「不适用」，不许拿演示内容冒充生产证据；演示/试跑的验收通过（含本站实测）只证明该演示部署，不等于生产环境 PASS。meta 描述统一为 150–160 字符（英文口径，标题 ≤60 不变；覆盖 v3.2.8 的 120–165；中文页面按展示宽度另行实测并在该篇记录里注明）。

**三、传产品增补**
1. **产品正文三段骨架**：H2 一「适合谁与用在哪」（用已确认事实，至少落一个具体规格或边界）→ H2 二「构造与规格」（材料结构连到应用，数字与规格表一致）→ H2 三「怎么订」（告诉买家确认配置要提供哪些输入，行动去向指到页面模块）。产品名带一个关键差异点（如容量/材质），不写裸型号；短描述 ≥40 字符（出处：母库 SKILL-INSTALL 版 site-content-and-aesthetics-spec 的校验最低线；一句讲清是什么＋给谁＋头号规格）。
2. **规格纪律**：规格值 ≤200 字符，长清单放正文、规格表只留短值；产品事实五状态（已确认/推断/缺失/冲突/过期），只有已确认能写进页面，推断显名、其余进缺口清单；更新产品先读现值，用户没提到的字段保留不清空。产品事实底稿旧模板的四状态表述以此五状态为准，引用旧模板时先对齐。
3. **上传纪律（接口路线执行细则）**：全量更新是替换语义，必须用现值＋真源合并重建，不复用旧 payload（空数组会真清空）；分类/标签传 ID；创建被静默拒绝且字段无误时，先换已验证分类建成、再改回正确分类；轮播与产品卡的价格/标签槽位不用就显式留空（平台会回填演示价格）；能力上下文（部署与 action 标识）每批刷新、约 25 分钟过期重取；新站可能没有产品创建接口、只能对既有草稿做更新式创建，按现场证据分支处理。
4. **媒体先行**：图片先转 WebP（目标 ≤500KB）并过分辨率/体积检查再上传；上传接口的标题/alt 参数不生效，上传后必须回写元数据并逐张复核（媒体库按名对账）；留一份媒体清单（文件名→地址/alt/许可/体积）。同页不重复用同一张图。
5. **数量门**：产品 ≥3、文章 ≥4 为成站线；产品 ≥2、文章 ≥3 为防空态底线（相关推荐区要够数才不露空态）；不够数时降级（撤相关推荐模块、列表页关工具条），并在交接记降级原因。单产品站、服务型站点可豁免数量门，豁免理由记交接（母库用户清单原有此豁免，保留）。

**四、CTA 与证据增补**
1. **价值交换**：每个主 CTA 在点击前要让买家知道——提交什么、得到什么、谁来回应、时效是否已验证；响应时效与保密承诺没验证就不许写，未知就显名未知。
2. **未验证路径不指示使用**：联系路径（邮箱/表单/电话）未实测可达前，正文与模块不得引导买家使用它；只能写明替代的已验证路径。
3. **产品链接证据梯**：链到产品族页只需族级证据；链到具体 SKU 须有「条件对规格」证据且目标页口径一致；每条产品事实（认证、性能、交期、适用性）进台账记出处与适用边界，无出处的事实降格为假设、不上页面。站内文案的 claim 同理：无证据的卖点只作内部假设，高风险 claim（首页主标语、广告、销售承诺）须有证据才许用。
4. **收资最小保护集**：任何收资入口（表单/邮箱/私信）上线前六项须实际确认（写了不等于确认）：用途（收来干什么）、禁止提交的数据（明确告诉买家不要提交哪些敏感信息）、获准的安全通道（只用经批准的通道收资）、负责人与承接能力（具名负责人确认承接与回应时效；邮箱可达不等于有人承接）、保留与删除（留多久、删除/撤回能力经负责人确认真实可行）、失败退路（提交失败时买家的替代路径）。任一项未实际确认，不许开收资。
5. **CTA 按风格轨分口径**（见 references/laicms-风格档案.md「CTA 口径」）：B 端轨用报价与样品类动词（Get a Quote、Request Samples、Talk to Sales），购买阶段收完整询盘信息；C 端轨用问价与确认类动词（Ask for Price & Shipping、Check Availability、Ask a Question），收资只问到能答复为止。两轨的转化都只有询盘弹窗、页眉报价按钮与联系模块这一条真实路径（平台无购物车与在线支付），不许写 Buy Now、Add to Cart 类假按钮。

**五、页面结构与上线验收增补**
1. **落地页七段**：Hero（给谁/解决什么/什么结果）→问题→机制（如何解决，不只口号）→证据→Offer（交付物/流程/周期）→异议（价格/风险/切换成本/可信度）→CTA；验收用 5 秒测试：新访客 5 秒内说得出卖什么、给谁、下一步点哪。
2. **上线扫描**：全站空态词扫描（No content is available yet 等模板空态句）结果为零；演示联系邮箱可能收不到件——上线前换真实邮箱，并用浏览器实提一次表单验达；soft-404、多 H1 等平台表现缺口登记为平台边界，不用重复请求去「修」数据层。

**六、社媒增补（并入 §八 分发口径）**
1. **账号安全红线（硬闸）**：分级口径——默认级：AI 只产草稿、选题、日历与复盘，不直接操作社媒账号（不自动登录、发帖、评论、私信、加好友），发布与互动由人确认执行，插件只在用户明确授权且人工监督下辅助观察，凭据不写进任何库文件；授权级：仅当用户显名授权且走平台官方接口或已授权连接时，可按 §八 的受控流程代理发布（内容与去向逐条经用户确认）。模拟登录、批量互动、绕平台规则的操作在任何级别都禁止。§八 的既有分发流程按授权级执行，与默认级冲突时以本条分级为准。
2. **LinkedIn 单帖六段**：钩子（具体场景或冲突）→背景→洞察→证据/例子→要点回收→软 CTA；内容按八类轮换（赛道、痛点、关键词、方法论、产品方案、数据复盘、幕后、证据）；私信只触达有上下文的人、首条不硬推产品；复盘看目标职位互动与评论质量，点赞数只作观察、不作质量判据。
3. **短视频是素材工厂**：脚本六段（钩子→场景→演示→洞察→证据→CTA），15–60 秒，第一屏给场景或冲突；无声看字幕能懂、画面能看清证据、不泄客户与报价；高表现视频复用到产品页、案例页、开发信与广告，评论里的客户原话回流选题库。各平台单独适配（LinkedIn 重专业判断、短视频平台重标题字幕与速度），不一稿通投。

**七、不吸纳项（显名，防后人误并）**：母库文章合同的重型 verdict 机器（约 50 项判定、十几段的 fallback 合同行、收资 endpoint 的全套政策合同）不并入本 skill——对独立站日常发文过重；需要时按出处回母库 ID-0001 原文执行。文章创建的脚本控制器装配细节同理，只在第六条接口路线下按 B 仓适配器原文执行，本 skill 不复制其代码与合同全文。

**《交付硬闸增补（v3.2.13，2026-11-14）》**

1. **语言一致性闸**：开工先定站点语言（以站点设置语言为准，演示站默认英文）；全部标题、正文、meta、模块文案必须与站点语言一致。交付前全站逐页扫描异语言残留（英文站即查汉字），结果非零不许报交付；专名与真实引文为例外，须在交接里显名。教训来源：2026-11-13 演示站英文站里夹了两篇中文文章、站主走查才发现——把关不能靠人眼，靠扫描。
2. **正文深度下限（机检项）**：产品正文不少于 450 英文词（中文站按 800 字地板），三段骨架每段须有实质内容（场景/构造收益/订购要素），不许用重复句与空话凑数；文章单篇不少于 1,200 英文词（中文 2,000 字），阶段篇幅带在此地板之上执行。发布前审计记录逐篇填实测词数，未达下限不许发布。
3. **CTA 钩子闸**：每篇文章结尾收口段与每个产品页行动段，价值交换三要素缺一不许发布——买家提交什么、换得什么（样品包/清单/报价等具体物）、谁在多久内回应。只写「联系我们」「了解更多」不算钩子；钩子必须是买家愿意留资的具体理由。与五阶段合同冲突时以阶段为准：Learn 等不收资阶段的钩子用页内自检、资料清单等不收联系方式的价值交换承接（「提交什么」相应改为买家付出的自查动作），不强行收资。

### 美化细节清单（逐项口径，2026-11-13 逐页评审回落）

- **数字全站一个值**：评分、产品数、年限、客户数这类数字，在首页、关于、页脚各处只许出现一个值，改造清单逐项对齐，对不上以事实底稿为准改齐（实测教训：首页 4.9 分与关于页 4.8/5 并存）。
- **命名全站一套词**：同一栏目在导航、页面标题、模块眉题、页脚里只许一个叫法，改造清单专列一项逐处核对（实测教训：同一栏目四种叫法并存）。
- **图文必须对得上**：每张图要与所在模块的文案主题对得上、图注属实，对不上就换图或删图注；同一张图不在多个页面当主图复用。
- **分类与标签名从简**：筛选控件宽度有限，长名会被截断显示，命名优先短词，建分类时就按前台显示效果取名。
- **卡片空洞是模板结构**：卡片内部「标题在上、正文贴底」的中部空洞靠增减条目数与文案长度缓解，不硬调间距；页面底部大空白先查空模块与隐藏残留，再考虑动全局间距基准。
- **单页也要有下一步**：关于、联系等单页收尾要有行动入口（联系或订阅模块），没有行动入口的页面在美观评审的功能性上扣分。
- **运行时页面不在美化范围**：404 等平台运行时页面样式由平台定死，登记边界，不耗时间。
- **页眉半透明属平台边界**：缓解靠内容层，Hero 图避开高对比区域与文字压顶，不指望开关解决。

- 模块只从后台设计器现有的模块里选，不自创结构，每个模块里能填的字段都点开填上，连看起来次要的标签、按钮文案、图片说明都不要空着，空着就会被模板默认值回填成演示内容，填完逐模块扫一遍演示词，一次清零。

- 网格的列数要等于条目数，设了几列就放几个条目，条目不够就改列数或补条目，不留空白卡在页面上。

- 大标题不要写太长，太长会断成孤零零的一行，具体多长合适第一次排版时看前台效果定并记进交接文件，长词不要放开头。

- 询盘表单必须绑站内真实存在的表单，绑错或没绑，前台只剩一个空壳，买家填了也收不到，绑完自己在前台试填一次确认能提交。

- 只有一个产品或一篇文章时，相关推荐区必然是空的，会显示没有内容的提示，要么删掉这个模块，要么先把目录补到至少两个再留它。

- 排版守几条，首屏要在几秒内给出答案和关键数字，数字加粗，单位写法全站统一一种不要混着写，段首一句话当小题、可以带编号，每隔三四段给一个视觉锚点，专业提示用标签段呈现不用表情符号，主按钮是看产品规格、次按钮是咨询帮选，按钮都放在讲完之后。

- 美化验收要看图，桌面和手机两种宽度逐页看一遍，导航能点、下拉挂对、轮播文案不是模板话、分类卡是真分类、页脚没有空白异常，地图显示灰块多半是外部地图的问题，不要当成自己页面的毛病反复改。

- 全站扫一遍空着的提示文案，凡是显示没有内容、敬请期待、表单没有字段这类字样的地方必须清零，列表页和详情页的页头文案也要换成品牌内容。

- 美化的终判据只有一句，一个陌生买家进来，能不能顺顺当当走完一次询盘，走不通就继续改。

### 发布终验和交付

- 全部内容完成后做全站终验，逐页打开前台，核对产品数字与资料原文一致，查演示品牌残留，查失效链接，查联系方式全站只有一种写法。

- 交付时给用户前台地址和后台地址，再逐页列受影响页面的直达链接，并列一份只需真人判断的测试清单。

- 绑自定义域名列为可选项，等用户点选后再做（流程见第六节），统计和站长关联按第七节的标准步骤做，不落下。

## 六、域名绑定全流程（适合所有域名服务商）

- 第一步查解析在哪、先读全量记录：先查这个域名的 NS 记录，NS 指向哪家，解析就在哪家加（常见有阿里云、腾讯云 DNSPod、Cloudflare、GoDaddy、Namecheap 等）。注册商和解析商可能不是一家，一律以 NS 为准，在注册商后台加了解析也不会生效，这一点先跟用户说清。动手加任何解析前，先把这个域名现有的全部解析记录读一遍、抄进交接文件（所有主机记录与类型，尤其 MX、TXT、SPF、DKIM 这些邮箱和验证在用的，还有 DNSSEC 开没开），后面每一步动记录都以这份全量记录为准，不许凭印象删改。各家生效速度差很多：GoDaddy 的解析生效比较慢，Cloudflare、阿里云、腾讯云的 NS 解析速度快得多；查到 NS 在 GoDaddy 这类慢生效的服务商时，只把等待预期跟用户说清——这是信息提示，不是建议他搬家——按慢生效的节奏等，不要误判成绑定失败反复改。换 NS（把解析搬到另一家）不是绑域名的默认动作，更不是治「解析慢」的默认建议：只有用户明确想换服务商时才提，并且必须走独立审批这一整套，缺一项不许动——先跟用户单独确认；把现有全部解析记录完整导出备份（连 DNSSEC 状态一起）；在新平台逐条建好并逐条核对无误；备好回滚办法（旧平台的记录先不删；但改回 NS 不是即时恢复承诺，必须预留 NS 与 DS 记录的 TTL 和各地解析缓存等待时间）；若 DNSSEC 已开启，先确认注册商父区 DS 与新平台 DNSKEY 的衔接顺序，按新平台与注册商要求先建立并验证新签名链、再移除旧 DS，无法协调 DS 交接时先按规范停用 DNSSEC 并等旧 DS 的 TTL 与缓存过期后再切 NS。完成这些准备才改 NS。改完先等相关 TTL 与缓存逐步过期，再从不止一个网络或公共解析器复查 NS、A/AAAA、CNAME、MX、TXT 与 DNSSEC 验证，当天用用户的企业邮箱收、发各测一封，确认邮箱没受影响；验收不过立即按备份回滚，并同样等 NS/DS 的 TTL 与缓存过期后复查到解析和 DNSSEC 都恢复，才算回滚完成，不要把「NS 已改回」当成已经恢复。

- 第二步先从 LaiCMS 拿目标：进站点后台的设置（Settings）里的域名（Domains）页面，把页面上方给出的 CNAME 目标原样复制下来——只复制纯域名，不带 https 前缀、后面不加路径，只能用本站给的这个值，不许自己编、不要用别的站的值套。这一步先只拿目标，域名本体等解析加完再回这个页面添加。

- 第三步打开服务商后台让用户登录：在 Muse 浏览器里打开 NS 对应那家的解析控制台，引导用户本人完成登录（账号密码走密码库、扫码或验证码由用户本人操作，不在聊天里收明文），登录成功后再由你接手操作。

- 第四步加解析：先在服务商的解析设置里给 www 加一条 CNAME，记录值填第二步拿到的 CNAME 目标；根域名（@）先看它上面有没有 MX、TXT 记录（以第一步抄下的全量记录为准）——没有时才按服务商支持的方式给根域名加解析，有 MX 或 TXT 时绝不给 @ 加 CNAME（见硬规矩②），改走服务商明确支持的 ALIAS / ANAME / CNAME flattening，或只绑 www 加跳转，再不行才用服务商给的 A 记录地址。回 LaiCMS 的 Domains 页面添加域名，先加 www 域名、再加根域名（根域名走跳转方式的，只加 www，根域名在服务商那边设跳转）。加解析时不要动原有的 MX、TXT 记录，那些多半是邮箱和验证在用的，删了会出事。注意四条硬规矩：① 记录值只填目标主机名，不带 http 前缀、不带网址路径；② @ 上已有 MX 或 TXT 时，绝不删除它们来给 CNAME 让位（同一主机记录上 CNAME 本来也不能与 MX、TXT 共存，删了 MX，公司邮箱当场就收不到信）；根域名改走服务商支持的方式：Cloudflare 按官网《Cloudflare 解析》页的做法（根域名加 A 记录、www 加 CNAME 并关代理、根域名 301 跳转到 www），其他服务商只用它明确支持的 ALIAS / ANAME / CNAME flattening（别名 / 拉平）——「明确支持」指服务商文档或控制台里写明这个功能能让根域记录与 MX、TXT 共存，名字相近但没写明支持的当作不支持、不许赌；都不支持就只绑 www 并把根域名跳转到 www。只有 A、AAAA 这类与网站本身相关的旧记录，才可以在用户确认后删除，且删除前把原值记入交接文件以便回滚；③ 根域名（主机记录为空或 @）很多服务商不允许直接做 CNAME，按规矩②的方式处理，不许硬填一个不被接受的值蒙混过关；同一个主机记录已有 CNAME 时，也不能再叠加 A、AAAA 等其他类型记录；④ **代理必须关**——服务商带代理或加速开关的（如 Cloudflare 的小黄云），这条 CNAME 必须关掉代理、只做解析，代理开着会挡住域名验证、SSL 证书也申请不下来，这是绑定失败最常见的原因之一，加完当场检查这一开关的状态并记进交接文件。

- 第五步验生效，按间隔复查：加完按实际采用的记录类型逐项查：www 查 CNAME 是否指向目标，根域按方案分别查 A、ALIAS / ANAME / CNAME flattening 或跳转是否生效，再回 LaiCMS 的 Domains 页面看三项状态——域名已添加、DNS 通过、SSL 通过，三项都过才算绑好，最后在浏览器里实际打开这个域名确认打开的是本站。注意 DNS 和 SSL 不一定同时过：DNS 已通过、只是 SSL 还没下来时，先等，不要删掉重配。域名加上以后绑定和 SSL 证书都不是立刻就能申请下来的，要留时间间隔复查：加完约 10 分钟看一次、约 20 分钟再看一次，中间不要连续刷新、不要几分钟内反复改解析；慢生效的服务商（见第一步）间隔还要放更长。10 到 20 分钟这个窗口内没下来先按等待处理，跟用户说清是在等生效、不是失败；超过这个窗口且复查仍不过，再进第六步排查。

- 第六步长时间验证不过这样排查：绑定状态长时间停在验证中，多半是验证环节出了问题，按顺序查——记录值有没有抄错或多空格、主机记录填的是不是界面要求的那一个、NS 是不是这家（加错服务商最常见）、同名冲突记录还在不在、代理开关有没有关。**删掉重加的前提是先确认解析本身没有问题**：按实际记录类型已经能查到对应解析、主机记录和记录值与绑定界面给的分毫不差、代理是关的——三样都确认了还长时间绑不上，才在 LaiCMS 的绑定界面把这个域名删掉、重新添加一次绑定，拿到新的绑定要求后把解析按新值核一遍（值没变就不用改解析），再走第五步验收；解析本身有问题时删了重加也没用，先修解析。

- 绑完回头补两件事：按第七节把 GSC 属性与验证迁移或补验一遍；站上页脚、联系页与询盘表单里的网址口径换成新域名，记进交接文件。

## 七、数据接入

### 接入步骤

- 建站收尾时先引导用户绑定他的 Google 账号，统计、站长后台和数据表格都挂在这个账号上，绑定走授权页由用户本人确认，不要让他把 Google 密码发到聊天里。

- 账号绑好后接 Google 统计（GA4），按官网教程的顺序一步步拆开做，每步单独验收（执行前先按第十一节的保鲜规矩读一遍官网最新版教程，本条是它的要点）：① 确认用户 Google 账号有建 GA4 资源的权限，公司已有 GA4 的不要重复创建，直接进管理里的数据流找现有那条；② 建或选一个 GA4 资源，再建或选网站数据流（选网站/Web，不要选成手机应用），网址框里只填域名、不重复带 https、末尾不加斜杠，拿到以 G- 开头的衡量编号——只复制这个编号，不要复制整段安装代码、不要粘脚本标签，UA- 开头的是旧版不能用；③ 回 LaiCMS 后台左侧菜单的「Google 追踪」，把编号填进 Google Tag ID 并添加；④ 用无痕窗口或手机打开前台真实访问一两个页面，再到 GA4 的实时概览里确认出现了活跃用户，实时数据一般等 1 到 5 分钟，收到才算接通，只填了编号不算。

- 再接站长后台（GSC），同样按官网教程拆开验收：① 先在谷歌搜 site:域名 粗查收录，新站查不到是正常的，不当故障；② 建或选站点属性，有域名解析权限时优先选「网域」属性，走 DNS 的 TXT 记录验证——主机记录填 @、记录值整段粘贴带 google-site-verification= 的原文，保存后等 10 到 30 分钟再回 GSC 点验证，域名在 Cloudflare 的可以走自动验证；说清当前用的默认域名能不能完成验证，不能就等绑了自定义域名再补这一步并记进交接文件；③ 提交站点地图前先自己打开 域名/sitemap.xml 确认能访问，再到 GSC 的站点地图里提交（输入框没带域名前缀就填完整地址、带了就只填 sitemap.xml），记下提交状态，刚提交显示无法获取是常见的，等几小时到一两天再看，不要反复提交；④ 域名后绑时回来把属性和验证迁移或补验一遍。收录和流量不承诺时间（教程口径是通常几天到几周），跟用户只说提交和验证的状态，不说多久起量。

- 引导用户把联系方式在站上更新到位，邮箱、WhatsApp 号码和地址逐项核对，联系页、页脚和悬浮钮三处写法一致，号码变了先改站上再开每日维护。

### 每日数据查看规划

- 每天固定看四类数据，但先把数据成熟度说清，不然会把没收齐当成暴跌：第一次给某个用户跑日报前，先当面确认报表截止时刻与时区，确认结果写进台账设置；未确认前只把默认每天早上 9 点、Asia/Shanghai 当作待确认建议，不自行当成用户口径；确认后固定按该截止时刻与时区出报表；统计按成熟日算——日报主报最近一个已完整结束、且平台数据已基本齐的那一天（站长后台 GSC 的数据通常要等一两天才齐，GA4 也有一天左右延迟）；当日未结束、平台还没更新到的数据只能标「暂定」，数据没回来的标「缺失」、不当成 0。每一类数据在台账和日报里都要标状态：完整 / 暂定 / 缺失，并分别写明该平台自己的实际统计日；GA4、GSC 与询盘渠道的成熟日不一致时逐项标日期，不许用一个总日期冒充所有平台的统计日；对比和涨跌只拿状态完整的成熟统计日和它前一日比，暂定与缺失只报状态、不下涨跌结论。四类是：① 访问数据（GA4）——访问量、用户数、主要来源；② 点击数据（GSC）——展示、点击、点击率、平均排名、收录页变化；③ 询盘数据——各渠道新询盘数，口径与本节询盘口径一致；④ 谷歌渠道带来的成效——归因这样记：每条新询盘在台账里记一个「来源」字段，取值只认能确认的：谷歌自然搜索、谷歌广告、直接访问、社媒、其他、未知。询盘表单能看到落地页或来源标记的按标记记，WhatsApp 和邮箱来的问得到、或对得上访问记录的才标来源，对不上就记未知，不许猜。这一占比统一标作「已知来源询盘中的谷歌占比」，分母是当日来源已知的新询盘总数；展示占比时必须同时展示来源未知数量，未知不进分母，也不许把未知硬算成谷歌或非谷歌；用户有成交记录时，再按同一来源字段统计谷歌渠道带来的收入。这一项要显名说清：GA4 和 GSC 本身都没有收入数据，收入只能以用户的台账和成交记录为准，他没有成交记录就不记收入、只报已知来源询盘中的谷歌占比，不许编收入数字。

- 看数据的节奏分三层：每日看被测成熟统计日与它前一日的对比（成熟日与完整/暂定/缺失的口径见上一条；异常报警的基线不含被测日，另按第八节口径算）；每周再做一次 7 日汇总，只汇总状态完整的那些天，缺的天显名标出，与上周同期对比；月度只看趋势（涨跌方向和大变化），不要每天报月度数。

### 台账与统计口径

- 每天的数据先落本地台账，再更新进一张 Google 表格台账，一天一行，列齐报表日期、各平台实际统计日、统计日状态（完整/暂定/缺失）、访问与搜索变化、各渠道新询盘数（每条带来源字段）、已知来源询盘中的谷歌占比与来源未知数量、当天发的文章和巡检问题，用户随时打开表格就能看全量，日报只是这张表的当日摘要。

- 新询盘的口径先定清：询盘指一个新客户第一次发来的、带明确产品或合作意向的会话或表单提交，广告、系统通知、老客户续聊不算新询盘。三个渠道分开数——网站询盘表单、WhatsApp、邮箱——每个渠道报它自己的新增数。

- 去重和日界这样定：同一个人同一天在两个渠道都来问，能按联系方式、或姓名加产品对上同一个人，就合并成同一条，总数里只算一次，渠道数里各算一次并注明已合并；对不上就分开算并注明未合并。按用户所在时区的日界切天（默认 Asia/Shanghai，用户在别处按他的时区）；第一次接上渠道时先记一条基线，基线之前的历史消息一律不算新增。提醒走单独的询盘轮询任务，轮询间隔、会话掉线重连、提醒失败时怎么在日报里补报，都在开启时和用户说清并验证一次，验证通过后再说提醒时效。提醒和进表格的内容只限已授权读取的渠道。

- 统计口径说清来源和日期，看不到的数据就写看不到，不要估算，不要把不同口的数据混在一起报。

## 八、每日运营

- 网站交付时问用户要不要开每日更新文章，用户点头后再建每日定时任务，不要默认替用户开。

- 三件事分开授权、分开建任务，不要混成一个每日任务：① 每日文章（默认一天一篇起步，按爬坡口径提量）；② 网站巡检（看打不开、缺内容、失效链接）；③ 询盘提醒（见第七节的询盘口径，需要单独的轮询任务）。用户可以只开其中一两件，每件都能单独关掉，关掉的方法当场告诉他。不要把每日任务说成全天候或即时：任务只能在 Muse 能运行、用户电脑和本地真源可达时执行（见第三节离线分支），实际延迟以任务真正跑通验证后的结果为准，验证前不承诺第一时间。

### 渠道提炼：痛点从哪来

- 渠道接上并经用户同意后，定期读他与客户的聊天和邮件，只提炼客户反复问的问题、担心的点和真实需求，汇总成痛点清单和选题库，客户姓名、联系方式、报价这类个人信息一律剥掉，聊天原文和客户信息绝不写进文章或网站。渠道的接法和只读不发边界见第九节。

- 用户还没给 WhatsApp 和邮箱权限时，不要干等，要主动去要：每日提炼靠的就是这两个来源，没授权文章就只能凭资料写、贴不准客户真实问题。在开启每日更新时、或者选题库见底时，主动向用户提出授权，并一次讲清四件事——读什么（只读与客户的沟通）、干什么用（提炼痛点喂选题）、边界（只读不发、个人信息剥离、原文不落盘）、怎么撤（随时能在已关联设备和授权页里取消）。他拒绝就把拒绝记进交接文件，不在同一件事上反复催；等场景变了（比如他问文章为什么不贴客户问题）再提一次。

- 选题库优先从沟通渠道提炼的客户痛点里取，痛点清单有新增就先补进选题库再排每日文章，让文章越写越贴客户真实问题。选题怎么验证、文章怎么写，按第五节写文章的细则执行。

### 发文节奏与发布

- 开每日更新前先和用户定一份选题库，选题从用户资料和客户痛点里来，一篇只讲一个点，写完按写文章的 SEO 口径检查再上传发布。发布额度只认一份有效授权记录，不靠记忆或惯例：开启每日更新时就建好这份记录，放进 30 任务清单层、并在交接文件里留指针，至少记四样——每日数量、生效日、选题范围（只发选题库内的，还是可含临时选题）、授权状态（有效 / 已暂停 / 已撤销）。发文量按爬坡来，不要一上来就定死：授权记录的每日数量初始值默认一天一篇（这只是初始默认值，不是写死的上限）；顺畅运行约一周后，主动建议升到一天两篇；约一个月后，再建议一天三篇。每次提量先经用户点头，并且选题库存量够才提——库存不够先补选题、不硬提量；他点头提量后当场改授权记录：新数量、他定的生效日（没说就次日生效）写进去，旧数量留一行变更记录（原数量、批准日期），不要直接覆盖没痕迹。此后每日任务一律按当日有效的授权记录发，记录是多少篇就发多少篇；用户想一直保持一天一篇也完全可以，节奏由他定，你只负责按节点提醒建议。

- 每日任务的节奏是先检查本地真源可达、登录后台、按当日获批额度写与发（额度只认本小节的授权记录，当天几篇就发几篇）、每篇上传发布后回前台读回验证、把链接报给用户，中断或失败当天就报，不要攒着。

- 防重复发布是硬规矩，按这个顺序做：每篇先定一个稳定任务键——站点加选题加日期，同一个键只许有一篇；先把定稿 Markdown 存到本地主本并记下任务键，再去后台发布；发布前先按标题和链接名查后台有没有同键的现存文章，有就接着核对那一篇，不要新建；发布成功立刻把后台的对象编号（文章 ID 或链接）回填进发布记录；如果发布动作做完但在读回或存档前中断，下次续跑先核验后台实际状态再决定补记还是重发，不许凭没记录就重建一篇。同一时段只许一个每日任务在跑，前一个没结束，后一个不要并发开工。跨账号迁移时，这里的查同键与单任务约束只是辅助防重复，不构成互斥或隔离，迁移启用门槛只按第十节执行。

- 每篇文章先以 Markdown 格式成稿再发布，发布后把这份 Markdown 原稿存到第三节定好的存档地，文件名带日期和标题。

- 每日文章同样只用已确认资料里的事实，不编造参数、证书和客户案例，资料不够写新选题时先报用户补资料，不要硬凑。

### 发布后社媒分发（固定收尾）

- ⚠️ **领英（LinkedIn）风控警告**：领英的风控非常严格，**不许全自动**——不许自动发布、自动加人、自动私信、自动点赞评论。领英只许「AI 写、人来发」：文案由你写好，交给人手动发出去；其余平台按各自规则和本小节的分发口径走。拿自动化工具碰领英账号，轻则限流，重则限制账号甚至封号，这个险不许替用户冒。本节下文的受控代理发布例外**不适用于领英**——领英在任何情况下都不许代发、不许自动化，只许人手动发。（与吸纳增补二「社媒增补」第一条的账号安全红线同向，本条是领英专条，口径更严。）

- **先出分享包，再走分发**：每篇文章发布验收后，先按 [references/laicms-社媒分享.md](references/laicms-社媒分享.md) 的规格生成一份社媒分享包——Facebook、X、领英、WhatsApp 四个平台各一份现成文案，钩子按那份文件的打法写，**领英那一份在包里单独标「人工发布」**。这份分享包就是下面所说「备帖」的固定成品，下面的归属、移交与防重复状态机都以它为对象执行；用户没在用的平台不硬凑版本，与下文口径一致。

- 每篇文章发布后顺带做社媒分发，这是发布动作的固定收尾，不是可选项。先把归属说死，全仓只用这一套口径：正式发布只有一个执行者——用户启用了社媒运营（social）模块时，发布只归 social 模块，建站（website）这边只备帖与移交；用户还没启用 social 模块时，按下面这个受控代理发布例外走，由 website 经授权代发——这个例外是全仓统一规则，模块地图与仓结构建议写的也是这一条，不许各文件各说一套。备帖这样做：从文章里抽一个客户最关心的点做钩子，配上文章链接和这篇文章的封面图，按用户在用的平台各备一版（领英 LinkedIn、Facebook、X 等，语气和长度按平台习惯调），帖文只用文章里已确认的事实，不另编卖点，用户没在用的平台不要硬凑版本。移交与发布这样分：已启 social 的，把文章链接、摘要和备好的帖文移交过去，website 不自己发；未启 social 的，默认把帖文连同发到哪个账号、配哪张图一起发给用户，引导他本人发，他复制就能发；他的社媒账号已绑定连接器、且他明确授权代发时，website 才按代理例外代发，代发前把最终帖文给他看一眼。防重复靠全仓共用的同一份发布记录（第十节同步清单里的那一份发布记录，website、social 和其他模块共用，不各记各的）：每篇文章在每个平台只建一条任务记录，至少记文章、平台、任务键、帖文版本、指定执行者、状态、移交时间、发布时间与结果链接；状态只许用下面五种并按状态机执行——**待移交**：帖文包已备好但尚未交给指定执行者，website 可完善、撤回或正式移交；已启 social 时 website 不得自行发布。**已移交待发布**：任务已交给记录中指定的 social 执行者（未启 social 且由用户本人发时，指定执行者就是用户），只禁止重复移交和 website 代发，不禁止首次发布；只有指定执行者可以接续同一条任务并改成发布中。**发布中**：指定执行者已经接下并正在发布，其他执行者不得再启动同一任务，执行者只能回填发布结果或改成结果不确定。**已发布**：已有可核验的发布链接，这是终态；只有已发布才禁止再发，任何人不得再发同一篇文章到同一平台。**结果不确定**：发布动作已经发出、超时或中断，暂时无法确认平台上到底有没有，所有人暂停重试，先由指定执行者查平台账号、已发布列表与共用记录；查明确已发布就改已发布并补链接，查明确未发布才退回已移交待发布，由原指定执行者继续。未启 social 且 website 按受控代理例外获授权代发时，website 就是该条任务的指定执行者，按同样状态从待移交进入发布中，不得跳过状态记录。用户日后启用 social 模块时，新任务的代理例外停用、只归 social；启用前已经进入已移交待发布、发布中或结果不确定的任务，仍由原指定执行者处理完，或在共用记录里显名改派给 social 后才由 social 接续，不许两边同时动。发不发、多久发一次由用户定。

### 巡检、日报与异常提醒

- 日常维护不止发文章，巡检任务按它自己的节奏看网站，打不开、页面缺内容、链接失效这类问题当天报用户；巡检频率和离线时的处理按本节开头的三件分开授权和第三节离线分支执行，不承诺全天候盯着。

- 每天的维护任务带一份日报，内容只报四件事：网站有没有新增访问和搜索表现的变化（按第七节的数据查看规划报，只报变化与异常、不贴后台原始数据）、有没有新询盘、新文章发了哪篇、网站巡检有没有问题，用大白话一屏报完。日报走两个通道推给用户，不要只发一处：Muse 里直接推一份，再从 Muse 邮箱发到他绑定的常用邮箱（绑的是微信关联的邮箱时，能联动微信提醒，他在微信上就能看到）。

- 异常不等日报，单独即时提醒，但先分清是业务异常还是采集故障，别把数据没收齐当成生意出事：① 阈值与基线这样定——对比基线用被测日之前最近 7 个状态完整的成熟日平均值，明确排除被测日；至少积累 3 个完整日才允许用基线触发报警，不足 3 个完整日只报数、不触发暴跌报警；有 3–6 个完整日时用已有完整日计算并在报警依据里写明样本天数；访问或点击较基线跌一半以上（跌幅 ≥50%）、且当日数据状态为完整，才算暴跌触发，跌幅没到线或数据还是暂定状态的只在日报里报变化、不单独报警。② 零基线单独判：基线本来就是 0 或接近 0 的（接近 0 指基线日均不足 1；新站、平时就没什么询盘属于这一类），归零不报警、只报状态；平时有稳定询盘、成熟统计日突然归零，才按异常提醒。③ 渠道掉线单独判：某个渠道的轮询断了、授权失效、读不到数据这类采集故障，报「渠道掉线 / 采集故障」并写清哪个渠道、从何时断的，不要写成「询盘归零」；故障期间该渠道数据标缺失、不进对比和占比。④ 站点打不开是可用性问题、不依赖数据成熟度，巡检确认打不开当天就单独提醒。任一真异常出现就当天单独提醒用户，不攒进日报里等；报警时把触发依据一并写清（哪一项、基线多少、当日多少、数据状态）。

## 九、渠道与可选绑定

### 接上用户的沟通渠道

- 建站时就引导用户把沟通渠道接上，先问他平时主要用 WhatsApp 还是邮箱跟客户聊，按他用得多的先接，不要两个一起推。

- 引导接 WhatsApp 时，用 `browser.browse` 在你的浏览器里打开 WhatsApp 网页版，把二维码呈给用户，让他用手机扫码登录，扫好后确认能看到他的会话列表再继续。

- 引导绑邮箱时，Gmail 和 Outlook 都走 Muse 的授权绑定，绑定后你能直接读邮箱，不要让用户把邮箱密码发到聊天里，也不要让他交出密码换登录。

- 用户只用电脑本地邮件客户端时，跟他说清本地客户端不能直读，同一个邮箱账号绑云端授权或在浏览器里登录网页版效果一样，引导他走这两条路，不要承诺能读他电脑里的邮件软件。

- 只读不发是硬边界：WhatsApp 和邮箱接上后只读不发，不代用户回复、不转发、不删改会话或邮件；需要发消息时先把草稿给用户看，他点头后也优先请他本人发，确需代发要单独得到他这次的同意。扫码前先告诉用户两件事：会话会一直挂在 Muse 浏览器里，他随时能在手机的已关联设备里退出；WhatsApp 对网页版自动化有限制，读取保持低频，不要高频反复刷新。发到用户常用邮箱和微信的只是提醒摘要，不带客户联系方式全文；聊天原文不落本地工作区，只存剥掉个人信息后的提炼卡。

### 可选绑定

- 这个小节的绑定全是可选项，用户愿意才绑，不绑不影响建站和每日更新，不要反复推销，一次问清就行。注意 WhatsApp 和邮箱不在这个小节的可选项里——它们是每日提炼的来源，按第八节的口径主动去要授权。

- Notion 有 Muse 的连接器，引导绑好之后，他存在 Notion 里的公司笔记和产品笔记可以直接当建站资料来源，选题库也可以放在 Notion 里维护，写文章时照着取。

- Facebook、Instagram 和 Messenger 都有 Muse 的连接器，绑好之后可以读客户在主页和账号下的留言与私信，提炼客户痛点，剥离个人信息的规矩和 WhatsApp 那个小节完全一样。

- 腾讯文档和微信目前没有 Muse 的连接器，不要承诺能直连，他用腾讯文档存资料，就在浏览器里登录腾讯文档网页版打开给你看，网页版打不开就请他把文件导出发给你。

- 微信里的客户沟通读不到后台，就请用户把聊天记录导出成文件发给你，或者把关键对话转述给你，再照样提炼痛点，不要让他以为你能直接翻他的微信。

### 找不到现成连接器时怎么办

- 先在 Muse 里查有没有现成的连接器或技能能干这件事。

- 找不到现成连接器时，先告诉用户缺什么，不要自行到网上找第三方工具装上；确需接入时，把来源、要的权限和维护方列清楚，用户点头后再装。

## 十、同步与换账号迁移

- 总原则：工作不绑在任何一个 AI 账号上。不管是 Muse 账号丢了、换了别的 AI 工具，工作都能接着干——靠的不是某个账号的记忆，而是把工作日志和流程全部回落成文件，文件放在用户自己名下。备份地在开工时就定好（见第二节），这一节讲平时怎么同步、换账号时怎么接。

- 回落什么（同步清单）：站点与产品事实底稿、内容清单、选题库与痛点清单（已剥个人信息的版本）、文章 Markdown 原稿、发布记录与任务键、每日数据台账、站点设置记录（域名与解析记录、GA4 衡量编号、站长后台属性、站上联系方式口径），还有交接文件与工作日志——做了什么、卡在哪、下一步是什么、哪些口径定过版，都写在里面，新接手的账号先读根索引和交接文件，就能知道全部状态和流程。永远不进备份地的：任何密码与令牌、客户个人信息（字段口径见下一条）、聊天和邮件原文。

- 选定的备份地（选 GitHub 时是用户自己的专属备份仓，不是官方 skill 仓；选 Google 云盘时是只许他本人可见的文件夹）是全模块共用的，不只装建站的东西：来发信等其他模块的工作状态同样回落到选定的备份地——产品档案（公司做什么产品、卖点与已确认事实）、公司信息。发布历史要记全：发过哪些文章（标题、链接、日期、任务键）、发过哪些社媒帖子（平台、链接、日期）都在发布记录里，新账号接手先看这份记录，才不会重复发、断了档。客户相关只回落公司级状态：公司名、官网域名、开发阶段、发过第几封、回没回、下一步日期；联系人姓名、邮箱、电话、聊天和邮件原文一律不进仓，只留在各模块台账（客户明细以台账为准）。每次往仓里推之前，先读回仓库的可见性，必须是私有才推；备份地选了 Google 云盘文件夹的，改查文件夹的分享范围，只许他本人可见才同步。用户要求删除某个客户的数据时，台账和仓里一并删，并记一条删除记录。

- 怎么同步：本地真源是主本。每日任务收尾固定做一次同步，按顺序来——先落本地，再同步到开工时选定的备份地（选了 GitHub 专属仓就推仓，选了 Google 云盘就同步到云盘文件夹，不默认两处都推）；同步完读回核验（仓里最新一次提交、或云盘里最新的一份，和本地关键文件对得上）才算同步完成，同步失败写进次日日报，不许静默跳过。Google 表格从本地主本生成、坏了能重建（展示层口径见第三节），不许反过来拿表格覆盖本地。

- 换账号怎么接（迁移五步，顺序不能反：先停旧、对账，最后才启用新任务）：① 接状态但不启用写入：在新账号里绑定同一个备份地（GitHub 或 Google 云盘）和同一个 Google 账号，拉取备份地里的文件，先读根索引与交接文件，把工作状态、流程口径和未完成事项接全。新账号的每日任务可以先建好但必须保持暂停；在互斥门槛满足前，不得启用任何会写站、发文、发送询盘提醒或改变外部状态的新任务，只许只读接状态、补授权资料和做对账准备。② 先拿到互斥证据：确认旧账号那边的每日任务（文章、巡检、询盘提醒）已经停用，能关掉的关掉并保留可验证证据——旧任务平台或调度记录显示已停用、旧端写权限或写授权已经撤销并读回确认等，证据记进交接文件。旧账号登不上、无法确认它停没停时，不许假定它已经停了，显名记「旧任务状态未确认」，新任务继续暂停；新旧执行时间错开、发布前查同键、发现旧账号活动后停新任务，都只是辅助检查和止损动作，不是隔离，不能据此启用新任务。只有两种情况可以越过这一步：一是已经拿到上述可验证的旧任务停用或旧端写权限撤销证据；二是新旧两端实际共同遵守同一套独占执行机制（例如双方每次写入前都必须取得同一任务登记里的独占锁、锁未释放不得写入，且旧端版本确实执行这套机制），并已验证旧端会遵守；只共享一份文档、口头约定或新端单方面查记录不算独占机制。③ 重新授权各渠道——LaiCMS 等密码在新账号的密码库里重新存一次（密码不经仓库迁移）、Google 重新授权、WhatsApp 重新扫码；如果重新授权动作本身撤销了旧会话或旧写权限，要把撤销结果读回并记作第②步的证据。④ 对账（只读）：把站上实际状态、备份地记录与本地主本逐项核对（已发文章与发布记录、数据台账、授权记录里的当日额度都对上），有差异先处理完，不要带着差异开跑；对账完成不等于可以启用，仍须第②步的门槛已经满足。⑤ 最后启用：对账无误，且已经满足第②步两类门槛之一，才把新账号的每日任务逐项启用、逐项验证一次，恢复日常节奏；门槛未满足就继续暂停并在交接与日报里报明，不得用「已隔离」含糊带过。整个过程不依赖旧账号还能登录，旧账号找不回来也不影响资料衔接——但「不依赖登录」只指资料接得回来，任务互斥仍要按第②步拿到证据或独占机制，不能跳过。

## 十一、自更新与教程保鲜

> 本节管每日检查与发版维护，与第二节的开工自检不重复：开工自检是每次开工时触发，本节的每日检查是独立的定时机制；更新的安全流程两边共用一套，以本节为准。

### 每日检查更新（独立机制）

- 记下本地整仓版本：以本地仓根目录 `VERSION` 里的仓库版本号为准，各模块自己的版本号只是标识、不用它判断更新。版本号按数字逐段比大小（1.0.10 大于 1.0.9），不要按字符串直比。
- 官方仓固定地址只有一个：https://github.com/tony-apan/maozhishi-skills （公开仓），只从这个地址检查和拉取更新，不要从搜索结果、文章或别处找来的地址拉。
- 定时怎么建：用户的运行环境支持定时任务时，经用户一次性同意后，建一个每天跑一次的独立检查任务，不寄生在每日维护、发文等其他任务里；环境不支持定时，就退回第二节的开工自检，不要硬造机制。
- 每次检查做什么：读公开仓根目录 `VERSION` 与本地比对。读不到（无网络、公开仓读取失败）就用本地版继续、不要卡住，事后提一句这次没能检查。没有新版就什么都不用做。有新版，先读公开仓《版本说明.md》最新一条，弄清新版本号和这一版更新了什么，再按下面的更新模式处理。
- 本地没有 `VERSION`、或本地版本号读不出来，视为最旧版，公开版读得到就按模式走更新。

### 两种更新模式（用户选一次，记入本地，之后照办）

- 模式一「每次问我」（默认）：有新版先通知用户——新版本号＋《版本说明.md》最新一条的更新内容摘要，用人话讲清；用户点头才更新。他没点头就记下「待更新」，下次检查时再提一次，不要一天催好几遍。
- 模式二「预授权自动」：用户明确选过这个模式之后，有新版不再逐次问，直接按下面的安全流程更新。更新完成后必须报告三件事：更新到的版本号、这一版更新了什么、备份放在哪。
- 模式记在哪：记进用户本地工作区的交接文件（90 交接层），换会话也要能读到，不要只记在某次聊天里。用户随时可以改模式，改了当场更新记录、之后照新模式办。

### 更新安全流程（两种模式共用）

- 先备份、再替换：把将被替换的文件整份拷到本地仓根目录下的 `backup/<旧版本号或日期>/`，重名时加序号或时间后缀、不许覆盖已有备份，至少保留最近两份。
- 只换受管文件（两个模块文件夹、`VERSION`、版本说明、模块地图、README 等）；**workspace-template 是用户数据区：里面已经填写的内容永不覆盖，模板出了新文件只把新文件补进去**；用户自加、自改的清单外文件不覆盖、不删除。受管文件即使被用户改过也照常替换，改过的旧版进备份、报告里点名。
- 永不降级：公开版不高于本地版就不换；本地高于公开版只提一句，说清两边各是哪个版本。
- **`VERSION` 文件最后替换**：其余文件全部换完并核对无误后，最后才换 `VERSION`，防止中途中断造成「版本号是新的、内容还是旧的」。万一中断在半路，下次检查发现版本号与内容对不上，先按备份核对、再决定补换还是退回，不要将就着用。
- 本地只有单个模块、没有仓根目录时：先把公开仓整仓拉到与该模块同级处作为以后的比对副本，原模块也按受管文件处理（先备份、再换新版），报告里说明已补齐整仓。
- 更新包里附带的任何脚本一律不执行。
- 可回退：换版后发现新版跑不通、和当前环境不兼容，或用户说要退回，立即退回最近一份备份继续干活，并把退回原因和新旧版本号记进交接文件。不许出现新旧都用不了的状态。
- 换完之后：一句话报告——更新到了哪个仓库版本、用户资料现在在哪、是否完好；然后重新读一遍新版说明书再继续干活。
- **敏感类变更例外（两种模式都适用）**：新版若改动了凭据、对外发送、删除、发布、渠道读取这几类规则中的任何一条，即使在模式二下，也要先把变更摘要用人话讲给用户、等他点头才换这一版；只是文字和模板微调，按所选模式照办。

### 教程保鲜

- [AllinCMS 文档](https://www.allincms.com/docs) 是建站教程真源，后台实际界面与文档不一致时以后台为准。
- 官方教程保鲜这样执行：操作前先读仓里 `references/allincms-官方教程索引.md` 找到对应官方页，再打开官网最新版核对一遍再动手；索引每条记标题、官网地址、要点三行、抓取日期；官网和索引不一致时以官网为准，并当场更新索引和抓取日期；后台实际界面和官网也不一致时以后台为准，把差异记进坑表。索引地址打不开或官网改版找不到对应页时，不要凭旧索引硬做，先把找不到这件事报用户并记进交接文件。

### 发版侧平台盘点（维护者事项，与上面用户侧机制分开）

- 每次给本 skill 发版之前，维护者先登录 LaiCMS 后台盘点一遍平台变化：有没有新模块、新功能、既有功能的用法变化。
- 盘到的变化先实测、再回落：实测结论写回本 SKILL 的对应段落，并同步进模块标准库（模块标准库建成后回落至 references/ 下的标准库文件），不要只写在发版说明里。
- 模块标准库见 `references/laicms-模块标准库.md`，为施工取值与巡检比对基线：施工时模块字段与量化取值以它为准，平台盘点逐项与它比对，差异先实测再回落更新。
- 盘点后没有发现平台变化，也要在发版记录里留一句「本轮已盘点、无平台变化」，不要默默跳过。

## 十二、附录：常用记录格式

- 下面六种格式是干活时随手用的记录样子，照着填就行，不用背，借鉴自原工具包的模板，砍掉了机器合同和英文状态码，只留人能看懂、网页路线用得上的字段，填好的记录都存进本地工作区对应的层里。

- 每次给用户报进度或者写交接，按六件说清，用了哪些资料、改了哪些文件、哪些是事实哪些是推断哪些还缺、哪一步要他点头、你打算怎么核对、结论记到哪个文件里，不要只报一句做完了。

- 产品事实底稿格式，一件产品一张，照下面填：
  - 产品名
  - 客户平时的叫法
  - 分类
  - 型号
  - 适合什么样的买家
  - 买家要办的事和他的痛点
  - 使用场景
  - 材质
  - 关键规格
  - 可选和定制
  - 起订量
  - 样品政策
  - 交期
  - 包装
  - 认证和测试
  - 贸易条款
  - 和同类比不一样在哪
  - 证据材料
  - 客户常问的问题和异议
  - 行动引导
  - 相关产品
  - 禁止写和没证实的说法
  - 每个值后面标状态和来源，状态只用已确认、推断、缺失、冲突四种，缺的和冲突的不许直接上站

- 文章选题单格式，每篇动笔前填一张：
  - 主词
  - 同义的其他说法
  - 要排除的词
  - 买家处在哪个阶段
  - 这篇的主任务，做什么、对什么产品或问题、看完能得到什么
  - 四种证据各记一行，买家任务、搜索需求、需求信号、搜索结果形态
  - 痛点六格逐格写，谁在疼、什么场景触发、缺哪份证据、怎么变成返工、对项目什么后果、看完能做什么决定
  - 开头答案先写好，做什么、要什么证据、什么条件、预期得到什么、证据边界在哪
  - 内链计划，每条写清作用、目标页、锚文本
  - 行动引导计划，主的、低门槛的、退路各是什么，验证阶段写清两轮各收什么
  - 不许出现的说法

- 客户原话提炼卡格式，每条客户反馈记一张，个人信息先剥掉再记：
  - 来源，哪个渠道、哪天、目标市场、买家是什么角色、聊的是哪个产品或场景
  - 客户原话要点
  - 触发场景
  - 痛点
  - 想要的结果
  - 顾虑和风险
  - 异议
  - 决策约束卡在哪，价格、起订量、交期、合规还是信任
  - 搜索假设，他可能会搜什么、处在哪个阶段、适合做成哪种页面、可信度高还是低
  - 转成的内容任务，拟标题、核心答案、要链到哪、行动引导是什么、哪天回头复查

- 图片清单格式，每张图记一行：
  - 编号
  - 原文件名
  - 用在哪个产品或页面
  - 用途，封面、图册、细节还是示意
  - 来源，自有、授权还是不确定，不确定的不许上
  - 处理结果，转没转 WebP、大小有没有压到 500KB 以内
  - 上传后媒体库里的标题和说明文字
  - 前台核对结果
  - 上传和补标题说明是两步，要分开记状态，上传成功不等于标题说明已经同步
  - 第一张图先单独走一遍全流程当测试，通过了再批量传其余的

- 发布记录格式，每发一篇或一件记一条：
  - 对象，文章或产品名加链接名
  - 稳定任务键（站点加选题加日期）和后台对象编号，发布前先查有没有同键现存对象，发布后立刻回填编号
  - 尝试状态，定稿已存、已发布待核验、已核验完成、结果不确定待核验四种里选一种，结果不确定时先核验不重建
  - 发布前定稿是哪一版，日期加标题能对上
  - 标题、摘要与搜索字段的最终值（按后台实有字段记，没有的字段不记）
  - 内链和行动引导实际落在哪些模块上
  - 发布时间
  - 后台状态
  - 前台核对结果，能打开、正文在、图在、链接能点
  - 效果只记哪天回头看数据，不写排名和询盘承诺
  - 回退办法，出问题改回哪一版或者先下线

- 故障记录格式，卡住或对不上时记一条，不要闷头重试：
  - 现象
  - 本来想做什么
  - 实际结果和报错原话
  - 按层排查的结果，资料齐不齐、事实对不对、字段填错位没有、账号有没有权限、是不是平台限制、网络问题、还是只是没核对到真实结果
  - 根因有多大把握
  - 能不能安全重试、重试前要改什么
  - 要不要回退、回退了没有
  - 哪些要用户拍板

## 发布后试跑补记（2026-11-13，首次全流程试跑实测）

以下为试跑实测注记，与正文口径不一致处以实测为准、待下版修订并入正文：

1. **入口**：laicms.com 与 www.laicms.com 当时 DNS 解析失败；真入口只有 https://workspace.laicms.com/sign-in ，不要从官网域名进后台。
2. **新站非空站**：新建站自带模板演示内容（3 个英文产品、3 篇英文文章等），「清理演示内容」是真实工作量，不是可选项。
3. **链接名连字符会被自动去除**（如 sample-product-a 变为 sampleproducta），与正文「连字符分隔」的写法预期不同，建链接名时按无连字符规划或建后读回确认。正文各处「连字符分隔」口径以本条实测为准。
4. **富文本粘贴被拦**：文章/产品富文本编辑器粘贴被拦截、只能逐字输入（正文「输入优先用粘贴」对富文本不适用）；逐字输入时个别空格不被保留，发布前逐段读回。（2026-11-13 冷跑复核：当前部署空编辑器一次粘贴约 9,700 字符成功，粘贴并非恒被拦；先试粘贴、被拦再逐字输入，以当站实测为准。）
5. **创建反馈慢**：点创建后按钮 Loading、列表骨架屏数秒，不要误判未响应而重复点击。
6. **发布徽章滞后**：发布瞬间徽章仍可能显示「未发布」，以顶部通知与列表状态为准。
7. **图片不传的后果**：图片字段非必填，但不传图前台是空白占位/破图图标，样张必须带图。
8. **模板品牌不随站名变**：页眉页脚品牌仍是模板自带的（实测为 Northstar Supply），须按改造清单逐页替换，不能以为改了站名就全站生效。
9. **平台没有「自动上传」入口**：平台内没有名为「自动上传」的 Skill 或 AI 写作入口（工作台侧栏、设置、编辑器、设计器、技能市场逐处查无）；设置里只有「AI 配置」页，未配置时 AI 功能不可用，启用须站主自备大模型 API（供应商、地址、Key、模型），与本 skill 的接口回放路线是两回事，不要向用户许诺平台自带自动上传。
10. **分类链接名同样去连字符**：分类 slug 同样自动去连字符（如 small-goods 存为 smallgoods）；分类没有独立路径页（/products/<分类> 返回 404），导航与筛选走 /products?category=<slug> 筛选页。
11. **发布有传播延迟**：新产品发布后前台 URL 有约 1 分钟传播延迟，短暂 404 先经列表页链接复核，不要急着判发布失败。
12. **重发刷新日期**：文章重新发布后，前台日期按平台时区刷新为重发日（实测 11-13 的文章重发后显示 NOV 14），介意日期的站重发前先知会用户。
13. **关联产品模块空态**：产品页关联产品模块在每分类仅 1 件时恒为空态且无数据源可配，处理法是隐藏该模块并发布，产品数上来后再打开。
14. **表单成功文案是平台固定的**：联系表单的提交成功文案是平台固定文案（Thanks. Your message has been sent.），与设计器里表单说明文案可以不一致，改不了，属平台边界；验收以实际提交成功为准。
15. **编辑器剪贴板快捷键不可用**：编辑器内剪贴板快捷键（Ctrl+X 等）不可用，段落跨节移动不要指望剪切粘贴，受限时接受现状并在交接里记明。
16. **媒体库可能产生重复条目**：媒体库上传同一张图可能产生重复条目，上传后顺手查一遍媒体库计数，重复的记交接。
17. **编辑器操作两则（2026-11-13 冷跑实测）**：① 正文 H2 用 Ctrl+Alt+2 施加，自下而上逐个转换后核对标题层级；② 文章编辑器当前只有标题与摘要两个字段（无独立搜索标题/描述字段、无文章分类字段），四字段一致以标题、摘要与前台显示为准执行。（已并入正文）
18. **前台验收防缓存假象**：长时间打开的页签可能读到旧图旧文案，验收一律刷新后以 DOM 为准（冷跑实测：关于页旧图为缓存所致、刷新即正）。
